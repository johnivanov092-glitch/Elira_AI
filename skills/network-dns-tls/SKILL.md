1. Для заданного URL/порта прочитай scenarios.md до команд. Зафиксируй точку
   (компьютер пользователя/backend/сервер/контейнер), имя, IP, порт, протокол,
   симптом, резолвер и время. При HTTP-адресе также прочитай ../web-research/SKILL.md:
   HTTP выполняй его http-командой, не своим PowerShell/Python HTTP-клиентом.
2. Проверяй последовательно DNS → TCP → TLS → HTTP → upstream. IP literal не
   требует DNS, HTTP без TLS — TLS не применим. Если DNS отказал, последующие
   уровни этого имени непроверены. Ping не заменяет TCP; remote listener не
   доказывает достижимость из клиента. У каждого уровня факт и свидетельство.
3. Для DNS различай системный resolver, hosts/overrides, split DNS, A/AAAA, TTL
   и отрицательный кэш. Один внешний резолвер не заменяет исходную точку.
   Для TLS проверь имя/SAN, сроки, цепочку, SNI и время; не отключай проверку.
4. 302 — редирект, 401/403 — результат конкретного запроса, 502/504 — сигнал
   проверки proxy/upstream, не доказанная причина. Сопоставь конфиг/ограниченные
   логи, Host/SNI, upstream имя/порт, bind, таймаут и фактический процесс. Host
   и контейнер могут видеть разное. SSH/IT Ops — общий linux-admin/admin.py,
   аргументы в ../linux-admin/scenarios.md; CIDR inventory — только по задаче.
5. Если запрошен файл: capability_load с {"group":"resources"}, затем встроенный
   resource_publish с {"project_path":"REPORT.md"} (настоящий относительный путь).
   Это не Python-модуль/CLI. Дай download_url; при конфликте имени повтори выдачу
   с уникальным download_name. Один путь на диске не выдача.
6. До правки DNS/маршрута/firewall сохрани значения и возврат доступа. После
   сравни до/после из той же исходной точки, учитывай TTL/кэш. Документацию версии
   читай при неизвестном контракте. Вывод: первый доказанный уровень отказа,
   доказательства и явно непроверенные уровни. Секреты не выводи.
