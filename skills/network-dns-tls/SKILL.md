1. Зафиксируй источник запроса, имя назначения, порт, протокол и наблюдаемую ошибку. Различай проверку с компьютера пользователя, backend, сервера и из контейнера: результаты могут отличаться.
2. Проверь уровни последовательно: разрешение имени, маршрут/адрес назначения, соединение с нужным портом, TLS, затем прикладной ответ. Один неудачный ping не доказывает недоступность HTTP; открытый порт не доказывает исправность приложения.
3. Для инвентаризации используй сценарий network_inventory из ../linux-admin/admin.py (параметры в ../linux-admin/scenarios.md). Не сканируй произвольные сети и все порты ради одной ошибки. Работай в пределах указанной цели.
4. При DNS проверяй фактический резолвер, нужный тип записи, TTL, локальные overrides и split DNS. При TLS — имя хоста/SNI, SAN, сроки действия, цепочку доверия и системное время. Не делай отключение проверки сертификата постоянным решением.
5. Для reverse proxy проверь внешний URL, upstream, bind-адрес, заголовки, таймауты и логи обеих сторон. Не считай успешный ответ proxy доказательством того, что обращение дошло до нужного backend.
6. Перед правкой маршрута, DNS или firewall сохрани прежние значения и способ возврата доступа. После изменения проверь из исходной точки пользователя, учитывая кэш и время распространения DNS.
7. В выводе укажи, какой уровень отказал, откуда проверено и чем подтверждено. Для неизвестных внешних контрактов обращайся к документации конкретного продукта и версии.

## Исполняемые сценарии

SSH и IT Ops реализованы в соседнем linux-admin; прочитай ../linux-admin/scenarios.md.
Запуск через run_bash. Встроенные ssh_* и itops_* больше не регистрируются.
