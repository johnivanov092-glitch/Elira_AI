  title: Изменение кода

1. Прочитай инструкции подключённого проекта, манифесты и фактические точки вызова. Проверь git status и область репозитория. Найди существующий модуль, тесты и принятые способы запуска; сохрани пользовательские изменения. Не создавай дублирующий runtime, registry, executor или слой хранения.
2. Объяви весь контракт исходного сообщения и принятых уточнений через runtime_control(operation="task_decide", config=...). Пример валидного config для one_off: {"disposition":"one_off","reason":"Исправление текущего модуля","targets":["module.py"],"requirements":[{"id":"req-compatible","text":"module.py сохраняет контракт прежних вызовов","mandatory":true}]}. Подставь фактические локальные targets, при наличии входных файлов укажи inputs. Для reuse/develop выбери соответствующий disposition и реально выбранный skill_name. Каждый самостоятельный обязательный результат, ограничение совместимости и условие отказа должен иметь стабильный id; используй уже сохранённые id/text. Решение о повторном использовании не даёт дополнительных прав выполнения.
3. Выбери минимальный связный патч. Перед изменением публичного интерфейса найди потребителей. Сохраняй формат файлов, кодировку, null/optional семантику, обработку отмены и ошибок.
4. Изучай зависимости по lockfile и коду проекта. Для незнакомого API или изменяемых внешних контрактов прочитай документацию соответствующей версии через web_search/web_fetch. Не выдумывай методы или параметры.
5. Проверяй наблюдаемое поведение и существенные риски регрессии: отказ зависимости, отмену, повтор запроса, границы данных. Не создавай тесты, повторяющие реализацию. После правки изучи свежий git diff и выполни подходящие проверки проекта; для UI нужен пользовательский путь, для API — фактический ответ, для данных — чтение прежнего состояния. Во время реализации запускай точечные проверки; финальные обязательные проверки — после завершения связанных правок.
6. Подтверди каждый обязательный id через runtime_control(operation="result_verify", config=...): command запускает реальный checker, targets содержит проверенные локальные результаты, report_path указывает отдельный JSON-отчёт. targets должны существовать до запуска checker и оставаться неизменными во время проверки; создаваемые checker отчёты не включаются в targets. Checker заново записывает {"checks":[{"name":"наблюдаемая проверка","requirement_id":"id из контракта","passed":true}]} с вычисленным boolean. Успешно выполненная проверка возвращает exit 0 и при passed=false: это доказанное нарушение требования. Ошибка запуска или самого checker возвращает nonzero и считается сбоем выполнения, а не доказанным отрицательным результатом. Используй текущие входы, код и интерпретатор проекта. Exit 0, компиляция или несколько passed-пунктов не подтверждают весь контракт. Receipts привязаны к общей версии задачи: после изменения входов, кода, контракта или выбранной версии навыка заново проверь все актуальные обязательные требования.
7. После прямого уточнения пользователя обнови полный список requirements, сохраняя остальные пункты и id. Новому условию дай новый id. Для явно изменённого существующего условия используй тот же id и поле source_clarification=<номер принятого уточнения, начиная с 1> внутри его объекта в requirements; в text скопируй точную фразу изменения или добавления из этого сообщения. Можно опустить только вступление «Ещё поправка:» или «Уточнение к текущей задаче:». Runtime сохраняет прежний текст вместе с поправкой. При Resume сначала сверяй восстановленные цель, требования, уточнения и версию навыка; продолжение не обнуляет контракт и не делает старые проверки свежими.
8. Итог разделяет изменённое, проверенное, незавершённое, commit/push и запущенную версию. Если обязательный результат не подтверждён, назови его и оставшееся действие. Commit, push, публикацию навыка и развёртывание выполняй в рамках поручения пользователя, а не автоматически после тестов.
