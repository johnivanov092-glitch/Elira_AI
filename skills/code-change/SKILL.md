1. Прочитай инструкции подключённого проекта, манифесты и фактические точки вызова. Проверь git status и область репозитория. Для ревью оставайся в режиме чтения, если пользователь не поручил исправления.
2. Уточни контракт на основе задачи: входы, результаты, ошибочные состояния, совместимость и критерий завершения. Найди существующий модуль, тесты и принятые способы запуска. Не создавай дублирующий runtime, registry, executor или слой хранения.
3. Выбери минимальный связный патч. Перед изменением публичного интерфейса найди потребителей. Сохраняй формат файлов, кодировку, null/optional семантику, обработку отмены и ошибок.
4. Изучай зависимости по lockfile и коду проекта. Для незнакомого API или изменяемых внешних контрактов прочитай документацию соответствующей версии через web_search/web_fetch. Не выдумывай методы или параметры.
5. Тест должен проверять наблюдаемое поведение и воспроизводить риск регрессии. Покрой важные отрицательные случаи: пустой результат, отказ зависимости, отмену, повтор запроса, границы данных. Не создавай тесты, просто повторяющие реализацию, и не расширяй проверки без причины.
6. После правки изучи diff и выполни подходящие проверки проекта. Для UI проверь пользовательский путь, для API — фактический контракт ответа, для данных — совместимость чтения старого состояния. Во время реализации запускай точечные проверки; финальные обязательные проверки — после завершения связанных правок.
7. Ревью ранжирует конкретные ошибки по последствиям и указывает воспроизведение и место в коде. Итог реализации разделяет изменённое, проверенное, незавершённое, commit/push и запущенную версию. Не делай commit, push или развёртывание только потому, что тесты прошли: учитывай поручение пользователя.
