  title: Изменение кода

1. Прочитай инструкции подключённого проекта, манифесты и фактические точки вызова. Проверь git status и область репозитория. Найди существующий модуль, тесты и принятые способы запуска; сохрани пользовательские изменения. Не создавай дублирующий runtime, registry, executor или слой хранения.
2. Зафиксируй цель, обязательные результаты, ограничения и принятые уточнения; для нескольких шагов веди план через todo_update. При необходимости прочитай подходящий SKILL.md обычным read_file по пути из каталога навыков. Если нужные файловые или shell-инструменты ещё не доступны, подключи capability_load(group="project"). Решение о повторном использовании не даёт дополнительных прав выполнения.
3. Выбери минимальный связный патч. Перед изменением публичного интерфейса найди потребителей. Сохраняй формат файлов, кодировку, null/optional семантику, обработку отмены и ошибок.
4. Изучай зависимости по lockfile и коду проекта. Для незнакомого API или изменяемых внешних контрактов прочитай документацию соответствующей версии через web_search/web_fetch. Не выдумывай методы или параметры.
5. Проверяй наблюдаемое поведение и существенные риски регрессии: отказ зависимости, отмену, повтор запроса, границы данных. Не создавай тесты, повторяющие реализацию. После правки изучи свежий git diff и выполни подходящие проверки проекта; для UI нужен пользовательский путь, для API — фактический ответ, для данных — чтение прежнего состояния. Во время реализации запускай точечные проверки; финальные обязательные проверки — после завершения связанных правок.
6. Подтверди обязательные результаты обычным запуском подходящих тестов, сборки или проверочного скрипта через run_bash в интерпретаторе проекта. Долгую проверку запускай через run_server(action="start", kind="job", command=...), затем читай run_server(action="logs", pid=..., wait_seconds=...) до завершения; старт процесса ещё не означает успех. Различай обнаруженное нарушение требования и ошибку выполнения самой проверки. Exit 0 или компиляция не подтверждают весь результат. После изменения входов или кода повтори затронутые проверки.
7. После прямого уточнения пользователя обнови цель, ограничения и план, сохраняя остальные требования. При Resume сначала сверяй восстановленные цель, требования, уточнения и прочитанную версию навыка; продолжение не делает старые проверки свежими.
8. Итог разделяет изменённое, проверенное, незавершённое, commit/push и запущенную версию. Если обязательный результат не подтверждён, назови его и оставшееся действие. Commit, push, изменение навыка и развёртывание выполняй в рамках поручения пользователя, а не автоматически после тестов.
