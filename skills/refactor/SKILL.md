name: refactor
description: "Упростить код без смены поведения."
metadata:
  title: Рефакторинг
---

1. Установи цель упрощения и границы изменения по прямой задаче пользователя. Прочитай инструкции проекта, git status, архитектуру, вызывающий код и существующие проверки. Назови конкретную сложность, которую убирает изменение; перенос сложности или новый слой сам по себе не улучшает код. Используй существующий runtime, executor, registry и механизм хранения.
2. Зафиксируй исходное наблюдаемое поведение: публичные типы и сигнатуры, порядок и количество результатов, ошибки, null/optional, сериализацию, чтение старых данных, отмену и жизненный цикл ресурсов — только применимые границы. Запусти подходящие baseline tests и сохрани уже существующие failures. Если нет покрытия важной границы, добавь небольшую characterization-проверку через её реальный публичный вызов; не закрепляй известный баг как обязательное поведение.
3. Для поиска потребителей используй grep/read_file/project_map и доступные lsp_definition/lsp_references; LSP здесь не делает rename/refactor. Выбери минимальные связные шаги, после каждого проверяй затронутое поведение. Не смешивай рефакторинг с новой функцией, миграцией данных или исправлением иной ошибки без поручения пользователя; обнаруженный дефект опиши отдельно.
4. Загрузи code-change и навык языка по необходимости. Объяви полный контракт через runtime_control(operation="task_decide", config=...). Пример валидного config: {"disposition":"one_off","reason":"Упростить модуль с сохранением поведения","targets":["module.py"],"requirements":[{"id":"req-compatible","text":"module.py сохраняет контракт прежних вызовов","mandatory":true}]}. Подставь актуальные targets, inputs и все требования задачи; для reuse/develop укажи выбранный skill_name. Стабильные id должны покрывать цель упрощения и существенные инварианты, не внутренние имена helper-функций. Принятые уточнения и восстановленные при Resume требования сохраняются. Для прямо изменённого условия сохрани id, внутри его объекта requirements укажи source_clarification=<номер принятого уточнения, начиная с 1>, а в text скопируй точную фразу изменения или добавления. Можно опустить только вступление «Ещё поправка:» или «Уточнение к текущей задаче:»; runtime сохраняет прежний текст вместе с поправкой.
5. Подтверди эквивалентность одинаковыми входами до/после через существующие unit/integration tests или небольшой differential checker. Для состояния проверь чтение прежней сериализации и повтор операции; для async — отмену и cleanup. Не считай равное время выполнения или успешную компиляцию доказательством эквивалентности. Изменение производительности измеряй отдельно одинаковым сценарием и условиями.
6. После последнего изменения изучи полный свежий diff, выполни обязательные проверки проекта и runtime_control(operation="result_verify", config=...): command запускает реальный checker, targets содержит актуальные локальные результаты, report_path указывает отдельный JSON-отчёт. targets должны существовать до запуска checker и оставаться неизменными во время проверки; создаваемые checker отчёты не включаются в targets. Checker заново вычисляет {"checks":[{"name":"проверка инварианта","requirement_id":"стабильный id","passed":true}]} с boolean false при нарушении. После успешного выполнения checker возвращает exit 0 даже при passed=false; nonzero означает ошибку выполнения, а не доказанное нарушение инварианта. Покрой каждый обязательный id текущего контракта. Receipts привязаны к общей версии задачи: после изменения кода, входов, контракта или выбранной версии навыка заново проверь все актуальные обязательные требования.
7. Итог объясняет, какая сложность убрана, какие публичные контракты и данные проверены, результаты baseline/финальных проверок и оставшиеся ограничения. Отдельно сообщи о непроверенных платформах или запущенной версии. Commit, push и развёртывание выполняй только в рамках поручения пользователя.
