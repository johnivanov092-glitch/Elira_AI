  title: Ревью кода

1. Установи репозиторий, инструкции проекта и точную область ревью: ревизии, branch, staged/unstaged изменения или перечисленные файлы. Не редактируй проверяемый код, если пользователь поручил только ревью. Через run_bash прочитай git status и зафиксируй base. Для branch review используй согласованный merge-base; для ревью относительно конкретного commit сравнивай именно его. Для рабочей копии сравни base с текущими файлами, отдельно учти untracked-файлы. diff до HEAD не включает незакоммиченные изменения. Если base нельзя установить из запроса и состояния проекта, уточни его; уже известные файлы и контракт можно читать сразу.
2. Найди исходную задачу, принятые уточнения, требования совместимости и документированные стандарты. Проверь отдельно соответствие задаче и реальные ошибки исполнения. Учитывай весь контракт: несколько passing tests не означают, что реализованы все обязательные результаты.
3. Прочитай изменённые участки и их потребителей через read_file, grep, glob и project_map. При реально доступном LSP используй lsp_definition/lsp_references/lsp_diagnostics; отсутствие diagnostics или lsp_not_ready не равно отсутствию ошибок. LSP здесь не предоставляет rename или автоматический refactor. Свежий полный git diff через run_bash надёжнее усечённого diff в UI.
4. Проследи конкретный вход и путь исполнения: проверки доступа и данных, прежние состояния, отмена, таймаут, повтор вызова, конкурентные запросы, обработка ошибки и освобождение ресурсов. Для каждого finding сравни на одном и том же входе ожидаемое поведение из явного требования или документированного контракта с фактическим поведением из кода; покажи доказуемое расхождение. Проверяй только применимые риски. Отличай добавленный дефект от уже существовавшей проблемы; стилистическое предпочтение не выдавай за баг.
5. Для существенной находки дай воспроизведение или короткую цепочку вызовов, где нарушение следует из кода. Подходящую проверку запускай в изолированной среде существующим run_bash и командами проекта; сохраняй исходные failures и учитывай побочные эффекты тестов. Исправления, изменение конфигурации, commit и публикация требуют соответствующего поручения.
6. Отчёт содержит только actionable findings: приоритет, файл:строка, условие возникновения, нарушенный контракт, последствия и минимальное направление исправления. Если ожидание для выбранного входа не определено или фактическое поведение выполняет требование, исключи finding; недостающий контракт укажи только как границу проверки. В число ошибок включай только доказанные расхождения. Неопределённость обозначай явно. Если доказуемых ошибок нет, сообщи это и перечисли существенные границы проверки. Проверка формата отчёта не доказывает достоверность находок; чтение кода не заменяет неисполненный тест или проверку запущенной версии.
