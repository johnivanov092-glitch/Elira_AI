# Самообновление приложения

`scripts/elira_release.py` — отдельный служебный процесс на стандартной библиотеке
Python. Он запускается из исходной папки платформы; кандидат не заменяет этот
файл при установке. Это механизм релизов, а не дополнительный агент или executor.
Саморазвитие выполняется для поставленной пользователем задачи. Фонового поиска
улучшений этот механизм не запускает.

В контексте агента `ELIRA_PLATFORM_ROOT` указывает стабильную платформу, а
`ELIRA_RELEASE_ID` — запущенный кандидат. Команды ниже вызываются через существующий
shell; отдельного tool executor нет. Конфигурация читается из `ELIRA_CONFIG_ROOT`
(backend платформы), включая при запуске кандидата.

## Подготовка и проверка

Из корня платформы:

```powershell
backend\.venv\Scripts\python.exe scripts\elira_release.py prepare improvement-1
# Агент редактирует .runtime/releases/candidates/improvement-1 и её окружения.
backend\.venv\Scripts\python.exe scripts\elira_release.py verify improvement-1
backend\.venv\Scripts\python.exe scripts\elira_release.py request improvement-1
```

`prepare` создаёт локальный Git clone активного релиза без сетевого remote и
копирует его проверенное дерево и зависимости в собственные `.venv` и `node_modules`
кандидата. При первом запуске используется текущий коммит исходной платформы;
её незакоммиченные изменения не копируются. Python activation scripts и console/gui
entrypoints пересоздаются с путями кандидата; `VIRTUAL_ENV` и `PATH` также указывают
на него. Для установки Python-пакетов используй Python кандидата с `-m pip`.
Агент устанавливает новые зависимости
в окружение кандидата существующими инструментами. Интернет для истории Git и
переключения версий не нужен; ещё не скачанным зависимостям нужен источник пакетов.

`verify` реально запускает typecheck, сборку frontend, backend pytest и
`npm run tauri -- build --no-bundle`. Затем отдельный backend кандидата проходит
startup/health на временном порту и копии SQLite. Scheduler, обработчики фоновых
заданий и drift не активируются до admission. Проверка не вызывает LLM или agent loop.
Receipt связывает результат с содержимым исходников, зависимостей, frontend dist
и собранного desktop exe. Изменение любого из этих файлов требует новой проверки.
Учитываются также игнорируемые Git исходники; ссылки/junction внутри запечатанных
деревьев не принимаются, чтобы receipt охватывал фактически загружаемые файлы.

## Установка

`request` только записывает pending. В управляемом запуске supervisor ждёт окончания
текущей работы, закрывает admission новых запросов, останавливает старые backend
и desktop, сохраняет SQLite, запускает новый backend с проверкой release/instance ID
и новый скомпилированный Tauri UI. После этого открывает admission. Данные и журналы
остаются в общих `ELIRA_DATA_DIR` и `ELIRA_AGENT_RUNS_DIR`; локальная конфигурация
загружается из backend исходной платформы, а не из Git кандидата.

Папки диалогов также хранятся в общей `code_agent_sessions.db`, таблица
`workspace_state`, ключ `chat_folders`. Клиент загружает их через
`/api/code-agent/chat-folders`; изменения применяются отдельными транзакционными
операциями. Старый `localStorage` используется как кэш и импортируется только
при отсутствии записи в базе. Пустое состояние новой вкладки не перезаписывает
уже сохранённые папки. Ошибка загрузки не считается пустым состоянием.

У старого Tauri dev (`http://127.0.0.1:5173`) и готового приложения
(`http://tauri.localhost`) разные хранилища `localStorage`. При первом переходе
старую раскладку нужно импортировать из dev до открытия новой сборки либо
восстановить из резервной копии WebView2; release не может читать чужой origin.
С 26 сентября 2026 папки текущей установки перенесены в SQLite с сохранением
исходных ID и привязок; новые релизы читают эту общую запись.

Первый managed запуск начинается при следующем открытии `Elira.bat` после `request`.
До этого работающий dev launcher продолжает свою работу. Без файла
`.runtime/releases/enabled` сохранён прежний путь разработки через Tauri dev.
После включения каждый новый запуск использует реальный exe выбранной версии.

```powershell
backend\.venv\Scripts\python.exe scripts\elira_release.py status
backend\.venv\Scripts\python.exe scripts\elira_release.py rollback
```

`rollback` ставит предыдущую проверенную версию в pending. Неудачный startup до
admission автоматически возвращает прежний код и снимок SQLite. После admission
старые данные автоматически не восстанавливаются: это стёрло бы новые изменения
пользователя. Совместимость миграций с предыдущей версией остаётся обязательным
условием пригодного для отката изменения; универсального обратного мигратора нет.

Фаза переключения хранится атомарно через replace JSON-файла. При прерывании до
admission восстановление повторяемо; после начала admission сохраняются текущие
код и данные. Процессы оставшегося запуска распознаются по OS creation identity,
а backend дополнительно подтверждает instance ID и служебный токен. Чужой процесс
на занятом порту не останавливается. Действующие задачи откладывают переключение.
Запущенные через `run_server` конечные jobs и постоянные серверы/watch также
откладывают переключение. Перед `request` останови принадлежащий задаче watcher
существующим `run_server(stop)`, когда он больше не нужен; supervisor не теряет
его дескриптор и не обрывает чужую работу ради установки.
Активный Telegram receiver также откладывает переключение, чтобы не принять сообщение
в момент закрытия admission. При необходимости используй `runtime_control(telegram_stop)`
и дождись завершения текущего polling; `stopping` означает, что старый поток ещё выходит.

## Практические границы

Отдельный процесс и сохранённая версия обеспечивают восстановление после сбоев
кандидата. Они не делают компьютер неуязвимым к отказу диска, ОС, OOM или ручной
перезаписи файлов платформы с теми же правами пользователя. Код служб остаётся
отделённым от обычной установки релиза; разделение прав ОС здесь не вводится.

Сквозной тест `backend/tests/test_release_lifecycle.py` запускает реальные маленькие
child processes и проверяет отложенное переключение, failed startup/SQLite rollback,
идентичность проверенного содержимого и повторное восстановление. Это тест механизма,
а не свидетельство сборки и визуальной приёмки конкретного Tauri-релиза.
