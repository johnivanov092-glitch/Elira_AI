# Самообновление приложения

`scripts/elira_release.py` — механизм релизов на стандартной библиотеке Python.
Без установленной Foundation он работает как отдельный процесс из исходной
папки платформы. Windows Foundation использует тот же механизм из защищённой
установки службы. Кандидат не заменяет служебный код при установке. Это механизм
релизов, а не дополнительный агент или executor.
Саморазвитие выполняется для поставленной пользователем задачи. Фонового поиска
улучшений этот механизм не запускает.

В контексте агента `ELIRA_PLATFORM_ROOT` указывает стабильную платформу, а
`ELIRA_RELEASE_ID` — запущенный кандидат. Команды ниже вызываются через существующий
shell; отдельного tool executor нет. Конфигурация читается из `ELIRA_CONFIG_ROOT`
(backend платформы), включая при запуске кандидата.

## Windows Foundation

Ручной откат доступен в окне обновления и после успешной установки. Пользователь
видит две версии: активную и сохранённую для переключения. Третий релиз остаётся
скрытым резервом. Действие называется «Откатиться на прежнюю версию» или
«Обновиться на новую версию» по порядку установки релизов. Рядом с выбранной
версией пользователь подтверждает «Установить сейчас» либо выбирает «Позже». Запрос
передаёт ожидаемые active/previous; владелец проверяет эту пару под блокировкой
состояния, повторно проверяет seal и использует тот же drain/start/admission.
При смене выбранной версии старый запрос отклоняется. Опубликованная новая
версия, рабочий кандидат и актуальные пользовательские данные сохраняются.
Обычная CLI-команда `rollback` по-прежнему создаёт предложение; подтверждённый
UI-запрос добавляет `--expected-active`, `--expected-previous` и `--confirm`.
После возврата A становится активной, B остаётся доступной для повторного запуска
без изменений. Доработка B выполняется в её рабочем кандидате с последующей
обычной проверкой и публикацией нового ID; изменять уже опубликованный seal нельзя.
После успешного ручного возврата к более старому релизу Foundation создаёт предложение
повторной установки сохранённой новой версии. Оно доступно даже в старом интерфейсе через существующую кнопку
«Установить сейчас». Само предложение не подтверждает установку; рабочая версия
остаётся активной до явного подтверждения пользователя.
Foundation хранит три успешно запущенных релиза: active/previous и самый новый
оставшийся резерв. Только после подтверждённого admission удаляются более старые
опубликованные копии из учтённой истории установок. Кандидаты, данные, snapshots и
неучтённые старые архивы не удаляются. Ошибка очистки записывается в журнал и не
отменяет успешную установку; очистка повторяется после следующего успешного запуска.
Длительность задачи, подготовки и проверки обновления не ограничена. CLI
`foundation_client.py --wait` по умолчанию ждёт без часового предела (`--timeout 0`).
Таймауты IPC/health/startup остаются проверками доступности, а не бюджетом задачи.
Резервирование и восстановление SQLite исключают `data/webview2`: это живой
браузерный профиль окна Tauri, чьи эксклюзивные блокировки могут остановить
копирование. Базы приложения и чатов резервируются; браузерный профиль остаётся
на месте, в том числе при восстановлении старого snapshot с таким профилем.

Реализация находится в `scripts/foundation_service.py`, `foundation_windows.py`,
`foundation_storage.py` и `foundation_client.py`. Установка выполняется отдельно
через `scripts/install_foundation.ps1` с правами администратора. Простое наличие
этих исходников не означает, что служба установлена или приложение перенесено.
Текущая проверка и развёртывание записаны в
[отчёте Foundation](research/FOUNDATION_WINDOWS_ACCEPTANCE_RU.md).
Для уже настроенных нестандартных путей DATA/journals установщик требует явные
`-DataDir` и `-AgentRunsDir`, чтобы установка не скрыла существующую историю
новой пустой папкой. Он не переносит данные и не меняет UAC самостоятельно.

Служба `EliraFoundation` работает как LocalService с отдельным SID. Её Python и
служебные модули находятся в Program Files, состояние и receipts — в ProgramData.
ACL защищают их от неповышенного агента. Опубликованные релизы доступны ему на
чтение; кандидаты и выбранное рабочее пространство остаются изменяемыми.
Подготовка, сборка, тесты, операции с пользовательскими SQLite, backend и UI
запускаются под проверенным токеном текущего пользователя в его интерактивной
сессии. По умолчанию установщик использует `-ApplicationTokenMode limited`:
неповышенный Medium token. Явный `-ApplicationTokenMode administrator` сохраняет
уже имеющийся повышенный High token пользователя. Этот режим требует запуска
клиента от того же повышенного интерактивного пользователя; служба не повышает
права клиента сама. Режим закреплён в защищённой конфигурации и регистрации,
проверяется при IPC, создании дочерних процессов и восстановлении. Код кандидата
не импортируется в процесс службы. `-ValidateOnly` проверяет параметры и пути
установки без записи файлов, реестра или создания службы.

В режиме `administrator` администратор может изменять опубликованные файлы,
останавливать службу и менять её конфигурацию. Foundation обеспечивает отдельное
управление релизами и восстановлением, но не изоляцию от полного администратора.
UAC, учётная запись и системная политика установщиком не меняются.

Локальный IPC принимает только типизированные операции релизов с `request_id`;
общего запуска произвольной команды с правами службы нет. Повтор того же
`request_id` возвращает его запись, а не запускает операцию повторно. Долгая
проверка продолжается в службе после завершения CLI; её состояние доступно через
`operation_status`. Файлы логов находятся вне опубликованного дерева.

При зарегистрированной Foundation `Elira.bat` вызывает защищённый клиент службы.
Команды `scripts/elira_release.py` также перенаправляются в него, только если
`--platform` и `--port` совпадают с зарегистрированной установкой. Другой каталог
платформы с отдельным портом использует локальный supervisor для изолированного
стенда; порт рабочей Foundation для него запрещён. Для зарегистрированной
платформы несовпадающий порт или неполная регистрация означают ошибку. Неисправная
зарегистрированная служба не подменяется запуском старого supervisor. Закрытие
приложения обращается к Foundation: служба проверяет завершение работы и
останавливает свои дочерние процессы. Неожиданный выход дочернего процесса
запускает восстановление с паузой 5 секунд; три ошибки за 5 минут прекращают
повторные попытки до следующего `open`. Служба остаётся доступной для диагностики.

Понижение токена приложения не меняет политику UAC Windows. Встроенный
Administrator без Admin Approval Mode требует отдельного решения: проверка
отказов обычному medium-процессу не доказывает невозможность нового повышения.
Прикладной Bypass сам по себе прав Windows не добавляет.

## Подготовка и проверка

Из корня платформы:

```powershell
backend\.venv\Scripts\python.exe scripts\elira_release.py prepare improvement-1
# Агент редактирует .runtime/releases/candidates/improvement-1 и её окружения.
backend\.venv\Scripts\python.exe scripts\elira_release.py verify improvement-1
# Сохранить предложение пользователю; эта команда не устанавливает обновление.
backend\.venv\Scripts\python.exe scripts\elira_release.py request improvement-1
```

`prepare` создаёт локальный Git clone активного релиза без сетевого remote и
копирует его проверенное дерево и зависимости в собственные `.venv` и `node_modules`
кандидата. При первом запуске используется текущий коммит исходной платформы;
её незакоммиченные изменения не копируются. При первом `prepare` в новой Foundation
с существующей legacy-установкой исходником служит её выбранный active release:
проверяются ID, путь, receipt и полный fingerprint исходников, зависимостей и
сборки. Незавершённое legacy-переключение или изменённый seal прерывают подготовку.
Копирование выполняет пользовательский worker; исходный релиз остаётся прежним.
Receipt кандидата указывает исходные release ID, путь и hash; эти сведения
сохраняются после verify. Первый кандидат нужно проверить и активировать как
baseline до следующего изменения, чтобы у Foundation появилась своя предыдущая
проверенная версия. DATA и журналы берутся из явно заданных путей установщика,
а не переносятся в новый каталог.

Python activation scripts и console/gui
entrypoints пересоздаются с путями кандидата; `VIRTUAL_ENV` и `PATH` также указывают
на него. Для установки Python-пакетов используй Python кандидата с `-m pip`.
Агент устанавливает новые зависимости
в окружение кандидата существующими инструментами. Интернет для истории Git и
переключения версий не нужен; ещё не скачанным зависимостям нужен источник пакетов.

`verify` реально запускает typecheck, сборку frontend, backend pytest и
`npm run tauri -- build --no-bundle`. Затем отдельный backend кандидата проходит
startup/health на временном порту и копии SQLite. Scheduler, обработчики фоновых
заданий и drift не активируются до admission. Реальные LLM/embedding providers
в этом окружении выключены; pytest проверяет в том числе agent loop с
контролируемыми ответами. Startup probe пользовательскую задачу не запускает.
В Foundation после сборки создаётся отдельное защищённое опубликованное дерево;
пути Python entrypoints проверяются для этого конечного расположения. Рабочий
кандидат остаётся редактируемым. Receipt связывает результат с содержимым исходников, зависимостей, frontend dist
и собранного desktop exe. Изменение любого из этих файлов требует новой проверки.
Учитываются также игнорируемые Git исходники; ссылки/junction внутри запечатанных
деревьев не принимаются, чтобы receipt охватывал фактически загружаемые файлы.
Git branch/HEAD не входят в fingerprint: commit/push без изменения файлов не
аннулирует проверку. `verify` отказывается пересобирать выбранные active, previous
и pending ID до записи нового receipt: для изменения нужен новый кандидат.
Чтение и сверка существующего receipt разрешены. В legacy-режиме seal повторно
проверяется после startup probe. Команды сборки и тестирования в legacy и
Foundation выполняются без лимита длительности. `verified` подтверждает проверки кандидата, но не его
активацию и не визуальную приёмку настоящего окна Tauri.

## Установка

`request` сохраняет предложение в `state.confirmation` с `request_id`, `release_id`,
`sha256` проверенного релиза и `requested_at`. Оно не становится pending и не
запускает установку, даже если приложение простаивает или перезапускается.
Агент завершает запуск с честным итогом: проверено, ожидает пользователя.
Пользователь выбирает «Установить сейчас» или «Позже» в индикаторе обновления.
«Позже» оставляет предложение доступным; автоматического согласия по таймеру нет.

Подтверждение связано с конкретным предложением и проверенным содержимым релиза.
Изменённый кандидат или заменённое предложение нельзя установить старым нажатием.
Агент не вызывает `confirm` за пользователя и не имитирует нажатие кнопки.
Workflow Bypass разрешает выполнение инструментов, но не подтверждает установку.
Этот выбор проверяет существующий владелец релизов; UI только передаёт решение.

Для ручного действия оператора тот же контракт доступен как
`scripts/elira_release.py confirm <request_id из state.confirmation>`;
`ReleaseManager.confirm(request_id)` заново сверяет предложение, receipt и текущий
fingerprint. У Foundation `confirmation_id` в IPC обозначает это предложение,
а транспортный `request_id` служит отдельным ключом повторной доставки команды.
Агент не использует этот интерфейс для самостоятельного согласия на установку.

Только после подтверждения supervisor записывает pending. В управляемом запуске
он повторно сверяет pending с сохранённым `last_confirmation`: ID предложения,
релиз и hash. Старый pending без этого согласия не устанавливается при перезапуске.
Новое предложение не заменяет уже подтверждённую ожидающую установку.
Затем supervisor ждёт окончания текущей работы, закрывает admission новых запросов, останавливает старые backend
и desktop, сохраняет SQLite, запускает новый backend с проверкой release/instance ID
и новый скомпилированный Tauri UI. После этого открывает admission и проверяет
успешный ответ `activate`, затем `/health` с ожидаемыми release/instance ID,
`admitted=true` и `draining=false`. Неудачное подтверждение после начала admission
не откатывает пользовательские данные автоматически. Данные и журналы
остаются в общих `ELIRA_DATA_DIR` и `ELIRA_AGENT_RUNS_DIR`: новая версия получает
актуальные данные на момент переключения, а не старую копию проверки. Локальная конфигурация
загружается из backend исходной платформы, а не из Git кандидата.

Снимок и восстановление охватывают SQLite-файлы с расширениями `.db`, `.sqlite`
и `.sqlite3` внутри `ELIRA_DATA_DIR`, включая вложенные каталоги. Каждый файл
копируется через SQLite backup API. Это не резервная копия всех пользовательских
файлов или внешних сервисов и не общая транзакция нескольких БД. Согласованность
при переключении требует завершения работы прежнего backend; посторонние процессы,
пишущие в эти данные вне supervisor, этим механизмом не координируются.

Папки диалогов также хранятся в общей `code_agent_sessions.db`, таблица
`workspace_state`, ключ `chat_folders`. Клиент загружает их через
`/api/code-agent/chat-folders`; изменения применяются отдельными транзакционными
операциями. Старый `localStorage` используется как кэш и импортируется только
при отсутствии записи в базе. Пустое состояние новой вкладки не перезаписывает
уже сохранённые папки. Ошибка загрузки не считается пустым состоянием.

У старого Tauri dev (`http://127.0.0.1:5173`) и готового приложения
(`http://tauri.localhost`) разные хранилища `localStorage`. При первом переходе
старую раскладку нужно импортировать из dev до открытия новой сборки либо
восстановить из резервной копии WebView2; release не может читать чужой origin.
С 26 сентября 2026 папки текущей установки перенесены в SQLite с сохранением
исходных ID и привязок; новые релизы читают эту общую запись.

Без установленной Foundation первый managed запуск начинается при следующем
открытии `Elira.bat` после подтверждения установки.
До этого работающий dev launcher продолжает свою работу. Без файла
`.runtime/releases/enabled` сохранён прежний путь разработки через Tauri dev.
После включения каждый новый запуск использует реальный exe выбранной версии.
Для обычного запуска открывай `Elira.bat` из корня платформы; прямой запуск
`uvicorn`, `npm run tauri dev` или exe кандидата не заменяет managed supervisor.
Поле `active` в `status` — сохранённый выбор релиза, а не доказательство живого
процесса. После запуска `/health` должен подтвердить ожидаемые `release_id`,
`admitted=true` и `draining=false`.

```powershell
backend\.venv\Scripts\python.exe scripts\elira_release.py status
backend\.venv\Scripts\python.exe scripts\elira_release.py rollback
```

`rollback` предлагает установку предыдущей проверенной версии с тем же подтверждением
пользователя. Неудачный startup до admission автоматически возвращает прежний код
и снимок SQLite перед переключением; новый диалог подтверждения для восстановления
не нужен. После admission
старые данные автоматически не восстанавливаются: это стёрло бы новые изменения
пользователя. Совместимость миграций с предыдущей версией остаётся обязательным
условием пригодного для отката изменения; универсального обратного мигратора нет.

Фаза переключения хранится атомарно через replace JSON-файла. При прерывании до
admission восстановление повторяемо; после начала admission сохраняются текущие
код и данные. Процессы оставшегося запуска распознаются по OS creation identity,
а backend дополнительно подтверждает instance ID и служебный токен. Чужой процесс
на занятом порту не останавливается. Действующие задачи откладывают переключение.
Запущенные через `run_server` конечные jobs и постоянные серверы/watch также
откладывают переключение. Перед `request` останови принадлежащий задаче watcher
существующим `run_server(stop)`, когда он больше не нужен; supervisor не теряет
его дескриптор и не обрывает чужую работу ради установки.
Активный Telegram receiver также откладывает переключение, чтобы не принять сообщение
в момент закрытия admission. При необходимости используй Настройки → Telegram → «Остановить»
и дождись завершения текущего polling; `stopping` означает, что старый поток ещё выходит.

## Практические границы

Миграции Workflow SQLite выполняются в одной `BEGIN IMMEDIATE` транзакции,
включая создание таблиц и пересоздание частичного уникального индекса. Одновременные
обращения scheduler и API не могут пересоздать этот индекс между чужими миграциями.
При потерянном или серверном ошибочном ответе admission Foundation повторяет
идемпотентный `activate` до трёх раз только после проверки той же уже допущенной
версии и instance ID. Успешный HTTP ACK и повторная проверка health обязательны.
Принудительная остановка принадлежащего Foundation job не требует exit receipt от
уже завершённого runner; обычные завершения команд продолжают проверять receipt.


В legacy-режиме shell с теми же правами может остановить сам supervisor; после
этого нужен внешний запуск. Lock предотвращает конкурирующий штатный запуск,
но не является границей прав для произвольного кода. Foundation добавляет
разделение прав для неповышенных процессов и восстановление через Windows SCM.
Оно не защищает от администратора с полными правами, отказа ОС или диска.

`run_server` сохраняет новые журналы в `ELIRA_DATA_DIR/background_jobs/logs/`,
включая отдельный ключ проекта и уникальный идентификатор запуска. Старые
сохранённые handles используют прежний `log_path`. Запуск задания больше не
создаёт `.elira/servers` внутри проверенного релиза и не меняет его fingerprint.

Сквозной тест `backend/tests/test_release_lifecycle.py` запускает реальные маленькие
child processes и проверяет отложенное переключение, failed startup/SQLite rollback,
идентичность проверенного содержимого и повторное восстановление. Это тест механизма,
а не свидетельство сборки и визуальной приёмки конкретного Tauri-релиза.
