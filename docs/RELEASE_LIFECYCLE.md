# Релизы приложения и Windows Foundation

Контракт исходников сверён 18.10.2026. Более подробный прежний текст сохранён
[в архиве](archive/contracts-20261018/RELEASE_LIFECYCLE.md). Датированные proof и
указанный там release ID не доказывают состояние установленной версии сейчас.

## Владельцы и границы

| Владелец | Назначение |
| --- | --- |
| [elira_release.py](../scripts/elira_release.py) | Кандидат, verify, предложение, переключение и восстановление |
| [foundation_service.py](../scripts/foundation_service.py) | Windows SCM/IPC adapter того же менеджера |
| [foundation_windows.py](../scripts/foundation_windows.py) | Токены, identity процессов, Windows IPC |
| [foundation_storage.py](../scripts/foundation_storage.py) | Защищённое опубликованное дерево |
| [foundation_client.py](../scripts/foundation_client.py) | Типизированный клиент оператора |
| [install_foundation.ps1](../scripts/install_foundation.ps1) | Установка и регистрация Foundation |
| [release_status.py](../backend/app/application/runtime/release_status.py) | Состояние владельца релиза для UI |

Зарегистрированная Foundation владеет запуском/закрытием приложения и релизами.
Без неё работает legacy supervisor; отдельный каталог и порт используются для
изолированной проверки. Повреждённая регистрация Foundation не должна незаметно
подменяться unmanaged backend. Agent loop остаётся заменяемой частью приложения;
кандидат не подменяет код службы и не создаёт нового executor.

`ELIRA_PLATFORM_ROOT` обозначает платформу, `ELIRA_CONFIG_ROOT` — backend с
конфигурацией; `ELIRA_RELEASE_ID` — ID запущенной версии. Общие DATA и journals
берутся из конфигурации владельца. Они не становятся приватной базой кандидата
при обычной установке.

## Windows token и защита

Служба использует LocalService и отдельный SID; код/состояние/публикации защищены
ACL. Сборка, Python, backend/UI и работа с данными исполняются проверенным
интерактивным токеном пользователя. `ApplicationTokenMode limited` и
`administrator` имеют разные гарантии; Bypass приложения не меняет этот token.
Administrator mode сохраняет уже имеющиеся полномочия и не создаёт границу
изоляции от полного администратора. Установщик не меняет UAC сам.

Типизированные IPC operations имеют request identity и durable operation state.
Повтор одного transport `request_id` не должен запускать ещё одну операцию.
Этот ID отличается от идентификатора предложения установки. Никакого общего
произвольного shell с правами службы интерфейс не предоставляет.

## Подготовка и проверка

Сначала читается состояние текущего владельца. Команды из корня платформы:

```powershell
backend\.venv\Scripts\python.exe scripts\elira_release.py status
backend\.venv\Scripts\python.exe scripts\elira_release.py --help
```

`prepare <release_id>` создаёт отдельный редактируемый кандидат с собственными
зависимостями. Источник определяется менеджером и provenance receipt: это может
быть активный релиз, а не текущий `main`. Незакоммиченные изменения checkout не
считаются автоматически перенесёнными. Поэтому перенос согласованного патча
в кандидат и соответствие его исходников проверяются явно.

`verify <release_id>` запускает typecheck, frontend build, backend pytest,
Tauri build и isolated startup/health probe. В проверке используются отдельные
данные, реальные model providers выключены. Проба не выполняет за пользователя
его продуктовую задачу и не подтверждает визуальное состояние окна Tauri.

Кандидат получает собственные Python/Node environments; console entrypoints
пересоздаются для его пути. Новые Python-пакеты ставятся Python этого кандидата
через `-m pip`. Working environment приложения и опубликованный релиз не являются
местом установки зависимостей нового навыка или кандидата.

Receipt связывает исходники, зависимости и собранные файлы. Изменение
учитываемых байтов требует новой verify. Git commit/branch сами по себе не
заменяют fingerprint. В запечатанных деревьях не принимаются ссылки/junction;
cache/pyc имеют предусмотренные менеджером исключения. Опубликованный ID и
защищённые active/previous/pending версии не пересобираются под тем же receipt.

Для оператора доступны `prepare`, `verify`, `request`; перед фактическим вызовом
выбирается согласованный ID и проверяется `--help`. Эти операции не выполняются
только потому, что изменена документация или отправлен Git push.

## Предложение и установка

`request <release_id>` сохраняет предложение с ID, release ID и проверенным
SHA. Оно не означает pending/установку. «Позже», простой и перезапуск не
подтверждают предложение. Установку подтверждает пользователь явным действием;
агент не нажимает кнопку и не вызывает `confirm` от его имени.

Подтверждение привязано к актуальному предложению и проверенным байтам.
Изменившийся кандидат не устанавливается старым подтверждением. В ручном
интерфейсе `confirm` получает ID предложения; transport operation request ID
остаётся отдельным ключом идемпотентности.

После подтверждения менеджер дожидается drain. Активные запросы, принадлежащие
приложению jobs/watchers и Telegram polling могут отложить переключение.
Ненужный watcher останавливает его владелец существующим инструментом;
чужая работа ради установки не прерывается.

Затем владелец переключает версию, запускает backend/UI, проверяет identity,
health и admission. Неудача до приёма работы запускает предусмотренное
восстановление/rollback. Данные восстанавливаются только по контракту менеджера;
это не произвольное копирование старой БД поверх уже допущенной пользовательской
работы. Пределы восстановления описаны кодом и тестами владельца.

## Как проверить результат

Не достаточно строки `active` или одного HTTP 200. Сопоставляются:

- receipt/fingerprint опубликованных байтов и ожидаемый release ID;
- владелец процесса, instance identity и ожидаемый executable/runtime;
- `/health`: ожидаемая версия, admission и отсутствие drain;
- сохранённые operation/progress/confirmation результаты;
- доступность корректной предыдущей версии и границы rollback;
- реальный UI/задача, если они входили в приёмку изменения.

Исходники в `main`, build worktree, verified candidate, установленный процесс,
браузерный fixture и native Tauri проверка фиксируются раздельно.

## Переключение и хранение

Rollback использует текущую пару active/previous и явное подтверждение.
Возврат меняет пару местами; направление определяется историей установки,
а не лексическим сравнением release ID. Скрытая резервная версия, retention
опубликованных версий, рабочие кандидаты и shared DATA имеют разные правила.
Очистка установленного дерева не является разрешением удалить DATA/историю
навыков или редактируемый кандидат.

Тесты механизма: [test_release_lifecycle.py](../backend/tests/test_release_lifecycle.py)
и Foundation tests из зоны влияния Atlas. Изолированные Windows proofs сохранены
[в историческом отчёте](archive/research/FOUNDATION_WINDOWS_ACCEPTANCE_RU.md).
Они не объявляются актуальной установкой без новой проверки.
