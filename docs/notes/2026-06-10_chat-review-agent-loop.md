## 1. Общая оценка проекта

**Вердикт: ~8/10 по инженерной зрелости.** Фундамент (kernel, policy, тесты, доки,
процесс ревью Sonnet/Opus со stop-hook) выше уровня большинства агентских проектов.

Что подтверждено фактически:

- **Тесты:** 2843 passed (+11 subtests) за ~4:21, `tsc --noEmit` — 0 ошибок.
- **Масштаб:** backend/app ≈ 354 файла / ~39K строк; тесты ≈ 22K строк (покрытие
  по объёму >50%); frontend/src ≈ 48 файлов / ~12K строк.
- **Agent Kernel:** единый `application/agent_kernel/executor.py`, fail-closed
  семантика (нет ToolSpec / не классифицирован / неизвестный scope → блок),
  тиры `auto`/`require_approval`/`forbidden`, approvals с TTL и privязкой к args-digest,
  SSRF-guard, shell allowlist, `project_scope_id`.

Сильные стороны: тестовая дисциплина; честная документация (фиксирует только текущее
состояние и выученные инварианты); верная ключевая ставка — качество runtime
компенсирует слабости локальных 7B–30B моделей.

Риски/долги:

1. **Фронтенд отстаёт от бэкенда:** `EliraChatShell.tsx` ~145KB, ещё три шелла по
   47–65KB; нет тест-инфраструктуры (канонический гейт — только tsc).
2. **`application/` разросся до ~60 подкаталогов** с пересекающимися именами
   (`memory`/`elira_memory`/`smart_memory`/`rag_memory`; `tools`/`tools_exec`/
   `tool_providers`/`tool_registry`; `workflows`/`workflow_engine`). Канонический
   путь по именам не угадывается. На диске пустые остовы `elira_phase19/20/21`,
   `elira_supervisor` и т.п. (остатки `__pycache__`).
3. **Потолок сложности vs потолок моделей:** runtime уже изощрённый; стоит по
   inference-телеметрии регулярно сверять, какие фичи реально меняют поведение модели.
4. **LAN/мобильный режим** (`Elira_Mobile.bat`) открывает бэкенд в сеть, где живут
   approval-эндпоинты и терминальные инструменты — наличие аутентификации не
   проверялось, проверить стоит.

## 3. Функциональное ревью цикла «задача → действие → ответ → результат»

Трассировка: `application/code_agent/agent_loop.py`, `agent_kernel/executor.py`,
`context/compaction.py`, `api/routes/code_agent_routes.py`, approvals
(`monitoring/store.py`), `frontend/src/components/CodeAgentChatShell.tsx`,
`application/chat/planner_v2.py`.

### Что построено правильно

ReAct-петля с SSE-событиями (`run_started`/`step_started`/`tool_call`/`final_response`/
`done`), отмена через реестр run_id, стрим переживает переключение вкладок (codeRuns),
anti-refusal промпт + regex-напоминание на «запусти/выполни», восстановление inline
tool-calls для моделей без нативного tool calling (balanced-JSON сканер + call-expression
fallback), умная обрезка tool-вывода «голова+хвост» (12K к LLM, 4K в событие),
inference-телеметрия на каждый LLM-вызов, авто-запись итога хода в RAG.

### Блокер: approval-петля незавершаема из приложения

`write_file` / `edit_file` / не-readonly `run_bash` по умолчанию `require_approval`, при этом:

- во фронтенде **нет ни одного упоминания approvals** (grep по `approval` в
  `frontend/src` пуст); поверхности одобрения — только Telegram и сырой API;
- одобрение матчится по 6 полям **включая `run_id`** и `args_sha256`
  (`monitoring/store.py: find_approved_approval`), TTL 300с;
- весь прогон живёт по умолчанию 180с (`DEFAULT_MAX_EXECUTION_SECONDS`), включая
  LLM-вызовы; цикл на `waiting_approval` не приостанавливается — модель получает текст
  и по правилу 5 промпта завершает ход «жду подтверждения».

Сценарий деградации: прогон завершился → пользователь одобрил в Telegram → следующее
сообщение = новый `run_id` → одобрение не матчится → создаётся новое → круг. Рабочий
путь один: человек одобряет за секунды, пока 7B-модель ретраит вызов с байт-в-байт теми
же аргументами в том же прогоне. Итог: базовый сценарий «создай/поправь файл» по
дефолтной политике штатно не проходит.

Варианты решения (на выбор, не план): inline-кнопка Approve в карточке tool_call
(прокинуть `approval_id` в событие — сейчас он только в тексте); пауза цикла с
поллингом статуса approval; привязка одобрения к сессии вместо `run_id`;
пер-проектный авто-тир для `fs.write` внутри `project_root`.

### Два логических бага серверной компакции

1. **Mid-run компакция теряет всю tool-работу.** `maybe_compact` → `summarize_history`
   → `_coerce_history` оставляет только user/assistant с непустым текстом; сообщения
   `role="tool"` и assistant с пустым `content` (типично при tool_calls) выбрасываются
   из входа суммаризатора. Длинным прогон становится именно из-за tool-результатов →
   при срабатывании (70% num_ctx) summary строится почти из ничего, агент забывает
   прочитанное, кроме последних 8 сообщений. Ирония: deterministic-fallback
   (`_deterministic_summary`) tool-результаты включает — запасной путь глубже основного.
   Коммит `0d28ffa` починил это на клиенте, серверный mid-run путь остался «мелким».
2. **Rolling summary обрезается не с той стороны.** `_merge_summary` добавляет новое
   summary в конец, `_cap_text` держит первые 4000 символов → при насыщении новые
   порции отрезаются, summary «окаменевает» на старейшем контенте сессии.

### Шероховатости

- **Обрыв по max_steps/дедлайну — без финального ответа:** `done(ok=false)` + красная
  плашка; файлы на диске уже изменены, а итога «что успел / что осталось» нет. Один
  финальный LLM-вызов без инструментов сильно улучшил бы UX.
- **Системный промпт противоречит deferred-режиму (P10.1):** промпт рекламирует
  `web_search`/`web_fetch`/`sandbox_run` (правила 9–10), но базовый набор их не
  активирует — вызов блокируется «activate via tool_search first». Обратное тоже верно:
  `todo_update`/`delegate_task` активны, но в промпте не описаны. Промпт стоит
  генерировать из фактического активного набора + описать `tool_search`.
- **Inline-парсер может съесть финальный ответ:** call-expression fallback распарсит
  фразу «я запустил run_bash(command=\"pytest\")» в финальном тексте как новый вызов →
  повторное выполнение вместо завершения.
- **Между ходами агент не помнит свои действия:** `buildHistoryPayload` шлёт только
  тексты; после хода с финалом «Готово.» агент не знает, что делал. После `0d28ffa`
  сжатая история информативнее несжатой — инверсия.
- Мелочи: событие `context_compacted` фронт игнорирует; текст «Approve at /api/…»
  адресован человеку, но скармливается модели.

### Чат-контур (кратко)

Planner v2 — честный keyword-роутинг (быстрый, детерминированный, override-able).
Потолок подхода: «нарисуй график в matplotlib» → route=image (SDXL вместо кода;
image проверяется первым), «найди баг в функции» без глагола правки → research
(веб вместо проекта). Co-occurrence-правила code_agent частично гасят, но однословные
запросы маршрутизируются по шуму.

## 4. Рекомендованные приоритеты (если/когда чинить)

1. Approval-петля: кнопка в UI + пауза/поллинг цикла — без этого код-агент не
   выполняет главную работу штатно.
2. Финальный summary при обрыве по шагам/времени — дёшево, заметно.
3. Глубокая серверная компакция (tool-результаты во вход суммаризатора) + обрезка
   rolling summary с головы, а не с хвоста.
4. Синхронизация системного промпта с активным набором инструментов.
5. Ограничение call-expression fallback (код-фенс / «почти пустой» текст).
