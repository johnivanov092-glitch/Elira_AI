# Web-auditor: live-кейсы связки (2026-07-10)

Задача (Джон): погонять реальные web-задачи на связке
`web_search → web_sitemap → web_fetch(store=true) → web_query → web_claim_add`,
собрать кейсы, где sitemap/search реально не хватает. `web_crawl` — только если
такие кейсы повторяются.

Прогон: 8 задач через живой code-agent (`/api/code-agent/run`, mode=search,
max_steps=14, bypass), реальный 35B + реальная сеть, флаг `web_corpus=1`,
backend на `ac80948`. Сырые результаты: `web_cases_results.jsonl` (scratchpad
сессии; сюда перенесены выводы, не мегабайты).

## Главный вывод: web_crawl НЕ обоснован

**0 из 8 кейсов упёрлись в отсутствие обхода ссылок.** Оба «крауловых» сценария
закрылись имеющимися средствами: C2 — sitemap идеально; C8 — sitemap нет, но
`site:`-поиск нашёл нужную страницу за один шаг. Ни в одном фейле недостающим
звеном не был link-following.

## Что реально мешает (повторяющийся паттерн — экономия шагов 35B)

Все 6 фейлов — **бюджет шагов, а не дыры связки**:

1. **Ре-запросы вместо финализации** (C1): факт уже в корпусе, модель делает
   10 web_query с перефразировками в поисках «идеальной» цитаты → near-dup
   loop-guard честно останавливает.
2. **Игнорирование собственного корпуса** (C3): PDF сохранён с паспортом
   «читай через web_query» — модель вместо этого перекачивает HTML-версию и
   уходит в bash.
3. **Мелкие вызовы вместо батчей** (C4: 5 отдельных web_search; C8: 6 вызовов
   web_claim_add вместо 1-2; батчинг обоих тулов существует и работает — C2/C5
   им пользовались).
4. **Перекапывание при готовом ответе** (C7): ответ в первом же сниппете.

Хорошее: wrap-up честный во всех фейлах (⛔ «Не завершено» + журнал фактов,
никакого сочинённого успеха); loop-guard сработал по делу; провенанс-механика
видна в бою (C2: перефразированные цитаты → честное «НЕ найдена дословно ✗»).

## Наблюдения второй линии

- **SearXNG «it»-категория шумит** на релизных запросах (MDN Git glossary как
  топ-результат для «FastAPI latest release»). Tier-теги при этом честно
  размечали мусор ([ugc] YouTube в C3).
- **GitHub releases** JS-тяжёлый и огромный — для релизов правильный путь
  `http_api` на api.github.com (модель пробовала, шаги кончились).
- **W5-дефект, подтверждён live и ПОФИКШЕН**: django пишет
  `og:article:published_time` (og:-префикс) — ключ отсутствовал в
  `_PUBLISHED_KEYS`, даты в реестре C2 показывались «дата неизвестна».
  Фикс + тест + live-проверка (`{'published': '2026-07-07'}`).

## Рекомендации (НЕ реализованы — на решение)

Рычаг — экономия шагов, не новая поверхность:
1. Правило/подсказка web-flow: «сохранил → 1-2 web_query → отвечай; claims
   ОДНИМ батчем» (⚠ базовый промпт на пределе — компакция-канарейки).
2. Для mode=search рассмотреть max_steps по умолчанию >14 ИЛИ мягкий нудж
   «ответ уже верифицирован — финализируй».
3. SearXNG: не подмешивать «it»-категорию в релизные запросы (клиентский тюнинг).

`web_crawl` не делать, пока повторные прогоны после (1)-(2) не покажут
кейсы, где реально не хватает обхода ссылок.
