# Выбор и жизненный цикл навыков

Elira выбирает навыки по смыслу задачи в существующем agent loop. Локальный
обучаемый `skill_advisor` только ранжирует подсказки; окончательный выбор остаётся
за Qwen. Отдельного маршрутизатора намерений, LLM-судьи или переключателя личности нет.

Подходящий установленный навык помогает работе, но отсутствие навыка не
останавливает задачу. Агент исследует окружение и документацию, создаёт
недостающее средство доступными инструментами, проверяет и применяет его в
текущем запуске. Полезное проверенное решение можно сохранить с инструкцией
и зависимостями. Это руководство для существующих file/shell/MCP-инструментов;
пакеты публикуются через существующий `runtime_control` и локальный Git.

## Создание и атомарная публикация

`skill_create(name)` возвращает `candidate_id` и каталог. Для улучшения существующего
навыка туда копируются его исходники; Python/npm окружение создаётся отдельно для
кандидата. Агент пишет `SKILL.md`, скрипты и фиксирует зависимости обычными file/shell
инструментами. Путь кандидата при публикации не меняется, поэтому его окружение
не переезжает и не подменяет окружение действующего пакета.

`skill_check(name, config={candidate_id, command})` запускает реальную проверку
через существующий shell runtime со Stop. Код проверки должен проверять результат,
а не просто печатать «OK». Исходники и установленные зависимости хешируются до и
после проверки; изменившийся пакет нужно проверить повторно. `__pycache__` и
временный кэш pytest не входят в содержимое пакета.

`skill_publish(name, config={candidate_id})` записывает исходники и lock-файлы в
локальный Git без remote и атомарно обновляет указатель активной версии.
`skill_load` может использовать её в той же задаче. Старый run сохраняет точную
версию своих инструкций и путь к скриптам до явного повторного `skill_load`.
Повторная загрузка проверяет новый пакет и заменяет снимок целиком; изменение
скриптов учитывается даже при прежнем тексте `SKILL.md`. Для MCP агент регистрирует/запускает
проверенный сервер прежними `mcp_upsert`/`mcp_start`; новый registry не создаётся.

`skill_status(name)` показывает активную версию, `skill_rollback(name)` включает
предыдущую, `skill_discard(name, config={candidate_id})` удаляет выбранный неактивный
кандидат. Рабочая и резервная версии сохраняются. Все изменения проходят прежний
Workflow permission mode; Bypass не получает дополнительных подтверждений.
История и пакеты находятся в `data/skill_development/` и не коммитятся в Git
приложения. Пакет выполняется отдельным процессом; его Python не импортируется
механизмом навыков в backend.

## Накопленный опыт и результат задачи

Навык служит структурированной подсказкой: условия применения, проверенные
действия, проверка результата, известные ограничения. Qwen выбирает применимость
по текущей цели и окружению, может изменить подход и улучшить пакет. Версии и
откат обеспечивает существующий локальный Git; таблица ключевых слов не выбирает
инструменты и не заменяет рассуждение модели.

Thinking использует те же инструменты и сохраняется на последующих модельных
шагах после их выполнения. Предварительный структурированный план может выбрать
группу `web` и запланировать исследование; поиск/чтение выполняет общий цикл.
Рабочая подсказка рекомендует первичную документацию, когда текущих данных
недостаточно, затем уточнение плана, выполнение и проверку. Постоянный поиск для
каждой задачи не включается. В сохраняемом навыке модель указывает использованные
ссылки, применимую версию и различает сведения источника с проверенным выполнением.
`web_search`, `web_fetch` и браузер сохраняют источники в прежнем журнале задачи.
Для браузера ссылка относится к фактическому конечному URL и прочитанному DOM;
текст переданных действий не включается в цитируемый материал. После Resume
источники и ссылки ответа восстанавливаются из журнала.
Без сети остаётся доступен сохранённый локальный пакет; внешние API и отсутствующие
зависимости по-прежнему требуют соответствующего доступа.

Перед разработкой новой возможности рабочая подсказка предлагает изучить
установленные навыки/MCP и подходящие внешние реализации. Модель сравнивает
применение готового, адаптацию установленного/внешнего кода и собственную реализацию.
Скачивание и Git используют существующий shell; внешние инструкции сначала
анализируются как материалы, а активный пакет проходит прежний lifecycle.
`SOURCES.md` в пакете хранит ссылки, commit/tag или версии, лицензию и атрибуцию
заимствованного кода, изменения и выполненные проверки. `SKILL.md` ссылается на него.
Улучшение уже подключённого MCP проверяется в кандидате; прежняя конфигурация
сохраняется перед обновлением конкретного подключения через `mcp_upsert/restart`.
Публикация пакета и обновление MCP — отдельные операции, общей транзакции нет.

## Обучаемые рекомендации

`skill_advisor.py` — локальная CPU-модель, которая учится связи пользовательской
задачи с выбранным навыком. Это рекомендация для Qwen: полный каталог остаётся
видимым, права и executor не меняются. Скачивание отдельной LLM и GPU не нужны.
Числовые оценки служат ранжированию; они не являются вероятностью успеха.

Источник обучения — существующий RunJournal завершённой задачи, `task_decide`,
загруженная версия навыка и свежий `result_verify` по всем заявленным результатам.
Проверка привязана к версии пакета, входам и выходам; перед обучением повторно
сверяются хеши файлов и отчёта. Замена выбранного навыка снимает актуальность
старой проверки. `done.ok`, текст «готово» или успешная команда сами по себе
не дают обучающего примера. Ошибки среды не превращаются в отрицательные метки.
Качество самой содержательной проверки остаётся ограничением: факт совместного
наблюдения навыка и результата не доказывает причинный вклад этого навыка.

Состояние модели хранится в `data/skill_advisor/`; источником фактов остаются
журналы задач. Публикация модели атомарна, версии доступны для отката.
`ELIRA_SKILL_ADVISOR_MODE=on` включает обучение и подсказки, `shadow` сохраняет
обучение и диагностику без подсказки модели, `off` отключает оба действия.
При недостаточном опыте, неизвестном запросе, другой версии пакета или повреждённом
состоянии Qwen продолжает обычную работу с полным каталогом. В журнале остаются
`skill_advisor_consulted` и `skill_advisor_learning` с результатом обращения.
`runtime_control(skill_advisor_status)` показывает состояние;
`skill_advisor_rollback, config={version}` выбирает сохранённую версию модели.

В первой версии из окружения используется только ОС клиента. Наличие GPU,
доступность сервера и зависимости Qwen проверяет текущими инструментами;
классификатор не определяет их по тексту. Если исходный запрос был обрезан
при сохранении RunJournal, задача выполняется обычно, но в обучение не попадает.

`runtime_control(task_decide, config={disposition, reason, skill_name, inputs, targets})`
фиксирует решение самой модели: `one_off`, `reuse` или `develop`. Для последних двух
нужно имя навыка. `inputs` и `targets` содержат пути исходных данных и результатов.
Это локальные файловые пути, не URL/URI: внешние адреса сохраняются в источниках
или `SOURCES.md`; для проверки конкретных внешних данных сначала сохраняется
их локальный снимок. `task_decide.targets` задаёт результаты задачи, а
`result_verify.targets` — файлы конкретной проверки. Ошибочный список исправляет
сама модель либо отдельно проверяет реальный дополнительный результат; runtime
не удаляет объявленные цели автоматически.
Решение и receipts сохраняет прежний RunJournal. После создания/исполнения кода
цикл напоминает о незаписанном решении; для `develop` проверяет публикацию и загрузку
той же версии. Разовая работа допускает `one_off` без создания пакета.

Необязательное `config.delivery` отдельно описывает выдачу файлов в чат:
`chat_download` с локальными `targets` либо `none` с пустым списком. Пропуск поля
при следующем `task_decide` сохраняет прежний контракт; явная замена сопровождается
`reason`. Это не список результатов для `result_verify`. Привязка опубликованных
байтов и проверка ссылок описаны в [ANSWER_CONTRACT.md](ANSWER_CONTRACT.md).

Пропущенный обязательный аргумент инструмента возвращается модели как ошибка
с именем поля. Это позволяет найти нужный ID существующими list/search-операциями
и исправить вызов. Настоящий запрос к пользователю и ввод секрета по-прежнему
используют отдельные операции Workflow; техническая ошибка сама его не создаёт.

Если опубликованный пакет был изменён на диске, `skill_status` показывает отличия
исходников от сохранённого Git commit: добавленные, изменённые и удалённые файлы.
Изменения зависимостей обнаруживает полный хеш пакета; их пофайловой истории в Git
нет. `skill_create` может скопировать изменённые исходники в новый непроверенный
кандидат. Старые файлы сохраняются, зависимости создаются заново, затем требуются
обычные check/publish/load. При публикации точкой отката остаётся последняя
целостная версия из текущей и предыдущей, если такая версия доступна.

`runtime_control(result_verify, config={command, targets, report_path})` исполняет
проверяющую команду существующим shell. Она должна прочитать реальные результаты
и записать свежий UTF-8 JSON `{"checks":[{"name":"проверяемое условие","passed":true}]}`.
Нужны непустые именованные булевы проверки, `exit=0` и неизменные файлы результатов.
Их SHA-256 и хеш отчёта измеряет runtime. Отсутствующий/старый отчёт, удалённый или
изменённый результат не получает pass; новая неудача снимает прежний pass для тех
же путей, включая Resume. Обычный успешный процесс и текст `True` не являются
подтверждением правильности данных. Качество самих проверок остаётся ответственностью
модели; при приёмке его оценивает независимый сценарий с эталонными результатами.

Перед запуском checker цикл фиксирует версию объявленных входов и выбранного
навыка. Если checker изменил вход, квитанция становится `unverified` до передачи
результата модели и в RunEvidence. Возвращение прежнего файла не восстанавливает
этот pass: нужны пересчёт результата и новая проверка. Такой исход не обучает
классификатор.

Актуальность включает текущий `code_input_epoch`, хеши входов/выходов/отчёта
и выбранную версию навыка. Последующее изменение состояния может потребовать
новой проверки даже при сохранившейся старой квитанции; Resume не повышает её
до текущего pass. Наличие обучающих примеров само по себе не означает, что
модель advisor уже активирована или её качество доказано живой приёмкой.

Sandbox хранит исполняемые исходники по SHA-256 и отдельные квитанции выполнений
до явного сброса sandbox. Последующий запуск не перезаписывает прежний исходник.
Одинаковые завершённые команды с одинаковым выводом и версией входных данных
вызывают подсказку для диагностики. Новый PID не считается продвижением; polling
того же процесса не считается повторным запуском. Эта подсказка не вводит лимит
задачи или дополнительное разрешение.

## Контракт

1. `task_skills.catalog_context()` читает установленный `skills/` и активные
   опубликованные пакеты из локального `data/skill_development/`, валидирует
   пакеты и добавляет только метаданные отдельным сообщением после стабильного
   системного префикса. Каталог не фильтруется по первой догадке о домене.
2. Модель вызывает `runtime_control` с `skill_list` или `skill_load`. При скрытой
   схеме доступен существующий `capability_load(group="runtime")`.
3. Обе операции идут через прежние registry/ToolExecutor/dispatch и относятся
   к чтению. Загрузка инструкции не запускает MCP, shell или скрипты пакета.
4. Цикл принимает успешный снимок, проверяет целостность и бюджет и закрепляет
   один блок активных инструкций существующим `pinned_message_ids`.
   Полное тело не дублируется в tool history. Порядок tool_calls → tool results
   сохраняется при вставке блока.
5. Событие `skills_changed` записывает снимки в существующее `active_skills`
   журнала. `tool_call.skill` содержит имя, заголовок, hash, причину выбора
   и признак повторной загрузки. UI показывает этот receipt в обычной строке
   инструмента; сохранённые диалоги используют тот же формат.
6. Resume/внутреннее продолжение восстанавливают снимки того же run_id. Новый
   запрос начинает отдельный набор навыков. Снимки не становятся личной памятью.

## Границы

- Корень инструкций принадлежит установке Elira; аргументы модели, подключённый
  проект, история, Library и Web не могут назначить другой корень.
  Новый пакет становится виден через явную операцию `skill_publish`, а не от
  наличия произвольного `SKILL.md` в пользовательском проекте.
- Имя пакета валидируется, выход через traversal/symlink запрещён. Пакеты
  с ошибками не превращаются в успешный пустой результат.
- Рекомендации навыка подчинены пользователю и Workflow. Личность, настроение,
  sampling, базовые инструменты и обязательные общие проверки не меняются.
- Выбор остаётся решением модели: наличие каталога не гарантирует правильного
  выбора на любом запросе. Неудачный выбор исправляется через полный skill_list.
- Если после начала работы с файлами/системой навык не выбран, цикл добавляет
  одно короткое напоминание в следующую существующую итерацию. Оно не блокирует
  инструменты, не назначает навык по ключевым словам и не создаёт вызов LLM
  только ради классификации. В обычной беседе напоминание не появляется.
- Короткие беседы не получают тела 12 инструкций. Каталог занимает дополнительный
  контекст, skill_load добавляет итерацию агента; влияние нужно измерять вместе
  с качеством выбора, отдельно от TTFT первого текста.

Формат пакета, лимиты и состав набора описаны в [skills/README.md](../skills/README.md).

## Проверки

`backend/tests/test_task_skills.py` проверяет реальный adapter/loop/journal,
отказ произвольным путям, полный каталог после ошибочного выбора, бюджет,
дедупликацию, normal/fallback compaction, Resume и изоляцию нового разговора.
`frontend/src/workspace/ToolCallGroup.skills.test.tsx` проверяет отображение
успешной и неуспешной загрузки в существующем интерфейсе.

Живой сценарий: беседа → диагностика Python → беседа; отдельно запросы по
Windows/Linux, сети, Java, JS/TS, Rust, SQL и развёртыванию. Оценивать выбранные
навыки, реальные инструментальные действия, prompt/cache/TTFT и корректность
ответа отдельно. Наличие подходящего skill не доказывает успешность самой задачи.

Повторяемая диагностика первого выбора (предложенные инструменты не исполняются):

```powershell
backend\.venv\Scripts\python.exe -u backend/tests/smokes/skill_selection_eval.py --live --output .agent/evals/task-skills/live
```

Сохраняются исходные запросы, ответы, seed, prompt/cache/TTFT и предложенные
навыки. `deferred_or_missed` означает, что первый вызов выбрал другой инструмент;
для оценки окончательного выбора нужен полный пользовательский путь.
