# Windows Foundation: проверка и развёртывание

Дата: 2026-09-27. Этот отчёт отделяет исправление механизма релизов от повторной
приёмки автономного агента. Исходный live Qwen сценарий остаётся **FAIL**;
его история находится в [отчёте автономности](AUTONOMY_ADVISOR_ACCEPTANCE_RU.md).

## Подтверждено

- Ошибка `run_server` исправлена в `ab01759`: новые служебные логи записываются
  в DATA, вне проверенного дерева. Проверены stdout/stderr, уникальность путей,
  отсутствие изменения дерева проекта и чтение прежних сохранённых логов.
- Установлена только тестовая `EliraFoundationProof`, запуск вручную,
  LocalService и отдельный SID. Production `EliraFoundation` не установлена;
  рабочая установка и её DATA не перенесены.
- Реальный `attempt-identity-access-4` получил
  `PASS_IDENTITY_AND_ACCESS_ONLY`: служба — LocalService в session 0,
  дочерний процесс — текущий Root, Medium, `elevated=false`, interactive session.
  32 проверки доступа получили Windows Access Denied для записи/удаления,
  смены владельца/DACL, остановки и изменения службы, завершения её процесса.
  Кандидат остался доступен на запись; canaries и служба сохранились.
- `relay-proof-2.json` и повтор на последней версии `relay-proof-3.json` подтвердили передачу русского stdout и stderr от
  пользовательского процесса в служебный лог, реальный exit code 7 и timeout.
  Эта проверка отдельно покрывает передачу вывода и завершение процессов.
- `attempt-lifecycle-3/lifecycle.json`: **PASS_STUB_RELEASE_LIFECYCLE**, 106,69 с.
  Два маленьких offline релиза прошли настоящий prepare/verify/publish и запуск
  из защищённого конечного пути. Проверены pending при активной работе,
  переключение после idle, failed startup с восстановлением строк и схемы
  `.db`/`.sqlite`/`.sqlite3`, принудительное завершение backend и автоматический
  запуск нового процесса той же службой. Откат кода после admission сохранил
  первоначальный и новый диалоги. Завершающий postflight независимо сверил
  receipts/fingerprints, строки трёх БД, отказы записи в опубликованный код,
  неизменную OS identity службы и отсутствие оставшихся тестовых процессов.
  51 наблюдение процесса и 13 worker observations подтвердили Medium token
  текущего пользователя. Отдельное конечное задание пережило перезапуск backend,
  продолжило писать вывод и было штатно завершено проверкой.

При review исправлена также атомарность резервной копии: публикация сначала
полностью копируется и fsync-ится в служебную временную папку, затем переименовывается
в конечную. Recovery не видит manifest неполной копии. Regression с настоящей
SQLite и отказом между manifest и database прошёл.

Первый lifecycle-прогон отказал из-за отсутствующего build output в тестовой
заготовке; второй — до запуска сценария из-за вызова несуществующего метода
тестовым checker. Исправлены именно fixture/checker; verifier не ослаблялся.

Доказательства находятся локально в
`.scratch/autonomy-advisor/foundation-proof/`. Неуспешные попытки сохранены
отдельно; их результат не заменяется поздней успешной проверкой.

## Проверки исходников

После объединения изменений backend pytest: **2491 passed, 72 subtests passed**,
302,88 с. Frontend typecheck/build и `cargo check` также прошли. Это проверки
исходников; они не заменяют receipt полного релиза и его запуск под Foundation.
PowerShell установщика прошёл синтаксическую проверку; новая рабочая установка
этим прогоном не создавалась.

## Обнаруженная настройка Windows

Текущий Root имеет SID встроенного Administrator (`…-500`). На момент проверки
`EnableLUA=1`, а `FilterAdministratorToken` отсутствует. По документации
[Microsoft](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpsb/7c705718-f58e-4886-8057-37c8fd9aede1)
это не включает Admin Approval Mode для встроенного Administrator.

Foundation создаёт и проверяет ограниченный Medium token для приложения даже
без linked token. Его обычные команды прошли проверку отказов. Это не доказывает
защиту от намеренного повышения прав при текущей политике учётной записи.
Системная политика, членство в группах, выход из сессии и перезагрузка этими
проверками не изменялись. После этой проверки пользователь решил оставить агенту
полные административные права и не включать Admin Approval Mode. Для такого
режима подготовлен [отдельный функциональный прогон](UNATTENDED_ADMIN_TRIAL_RU.md)
без заявления защиты от администратора. Рабочая Foundation этим решением
автоматически не устанавливается; её текущий протокол принимает неповышенный токен.

## Ещё не подтверждено

- Каноническая сборка и запуск полного приложения через установленную Foundation.
  Пройденный lifecycle использует маленькое offline приложение с настоящим
  ReleaseManager, WindowsProcessHost и Foundation recovery loop.
- Повторный live Qwen сценарий самостоятельного изменения UI/backend.
- Перенос и запуск рабочей Elira под Foundation.
- Длинный сценарий compaction/Stop/restart/Resume.

Тест маленького offline приложения проверяет механизм Windows и релизов;
он не заменяет сборку полного приложения, настоящее окно Tauri или автономную
пользовательскую задачу с Qwen.
