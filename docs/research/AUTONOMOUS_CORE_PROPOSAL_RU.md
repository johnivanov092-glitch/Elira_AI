# Автономная Elira: предложение по границам и обновлениям

Дата: 2026-09-26. Статус: границы согласованы пользователем; реализация и
проверка ведутся отдельно. Основание — текущий код и запрос пользователя.
Приложенные архитектура и стенограмма используются как справочный материал;
рекомендации веб-ассистента не создают полномочий или ограничений.

## Рекомендуемая граница

Неизменяемой в обычной работе должна быть небольшая основа запуска и
восстановления. Agent loop, контекст, память, frontend, прикладной backend,
навыки и интеграции могут развиваться. Явная задача пользователя или Bypass
определяет полномочия; повторное согласование уже разрешённых действий не нужно.
Удаление или изменение чужих пользовательских данных требует полномочий из
задачи/явного подтверждения. Создание своего рабочего кода — часть выполнения
задачи, а не отдельный запрос на разрешение для каждой строки.

```text
Tauri / служебная основа запуска
  ├─ активный релиз A: UI + backend + зависимости
  ├─ кандидат B: изменения + собственные зависимости + проверка
  └─ выбранный релиз / health / остановка / восстановление A

Внутри активного релиза:
  один agent_loop → один ToolExecutor → существующий runtime_registry
                                 ├─ файлы и shell
                                 ├─ MCP / API / CLI
                                 └─ навыки и повторно используемые пакеты
```

Основа запуска не планирует задачи и не становится вторым агентом или
исполнителем инструментов. Абсолютно неуязвимого backend не бывает: процесс
может завершиться, диск заполниться, ОС отказать. Цель — восстановимый запуск
и сохранённая работа. Git сам по себе не откатывает БД, окружения и процессы.

## Что уже есть и что отсутствует

| Часть | Подтверждённый владелец | Состояние до этой работы |
|---|---|---|
| Цикл и исполнение | `application/code_agent/agent_loop.py`, `application/agent_kernel/executor.py` | Уже единые |
| Интеграции | `application/tool_providers/runtime_registry.py`, `code_agent/tools/_runtime_control.py` | MCP можно зарегистрировать и включить в текущем run |
| Создание кода | Существующие file/shell tools и `resource_materialize` | Можно исследовать, написать и запустить адаптер |
| Навыки | `application/code_agent/task_skills.py`, `skills/` | Есть каталог, загрузка, hash, сохранение на Resume |
| Разрешения | `application/agent_kernel/impact_policy.py`, Workflow | Bypass уже существует |
| Запуск backend | `src-tauri/src/main.rs`, `start_backend` | Запускает текущий checkout и его `.venv` |
| Самообновление | Отдельного владельца нет | Нет проверенного candidate → active → rollback |

Пути `application/...` в таблице относительны `backend/app/`.

## Цикл создания возможности

1. Получить цель и уже выданные полномочия пользователя.
2. Осмотреть локальное окружение и имеющиеся средства.
3. Использовать подходящее рабочее решение; если его нет — исследовать и создать.
4. Проверить конечный результат и применить решение в исходной задаче.
5. Сохранить полезное решение как пакет: код, зависимости, инструкция, проверка.
6. При повторной задаче переиспользовать пакет; при поломке исправить кандидат.

Отсутствие skill не означает отсутствие способности. Не требуется отдельный
hardcoded обработчик каждой пользовательской задачи. STT/TTS разговора через
UI остаются инфраструктурой связи; обработка пользовательской записи должна
начинаться с анализа локального оборудования и условий задачи. Серверная
инфраструктура может быть предложена при необходимости, без неявной отправки
долгой задачи в голосовой CPU-сервис.

## Локальный Git и атомарное включение

Рекомендация: отдельный локальный репозиторий рабочих пакетов Elira без remote.
Для изменения самого приложения — отдельный кандидат из репозитория приложения.
Одна активная версия и предыдущая исправная версия нужны для восстановления;
множество сохранённых checkout не требуется. История кода остаётся в Git.
Удаление временного кандидата выполняется в пределах выданного разрешения на
его жизненный цикл; существующие пользовательские файлы не считаются мусором.

Состояния: `candidate → checking → ready → activating → active`, при ошибке
активации — `rollback`. Состояние перехода должно быть долговечным, чтобы запуск
после падения завершал переход или восстанавливал прежний релиз.

Проверка привязывается к конкретным исходникам, сборке и зависимостям; изменение
кандидата после проверки делает её устаревшей. Активное выполнение не получает
половину новой версии. В момент переключения нужно завершить/сохранить run,
остановить старый backend, выбрать целый релиз, запустить и проверить новый.
Восстановление продолжает прежний run через существующий журнал.

Для БД требуется отдельное решение: совместимые миграции либо согласованный
снимок и восстановление. Обещать rollback по одному Git commit здесь неверно.
Двойной запуск двух backend над одной изменяемой БД не обеспечивает атомарности.

## Laya

Испытание multilingual на CPU сервера (шесть физических ядер, 8192 токена)
дало 9 правильных маршрутов из 16. На почти 8К токенов модель пропустила задачу
в конце запроса. По решению пользователя эксперимент удалён из рабочего пути;
исходники сохранены в Git. Полный отчёт — `LAYA_CPU_EVALUATION_RU.md`.

Предварительный разбор и выбор инструментов выполняет основная Qwen в своём
обычном цикле. Старый семантический regex-классификатор не возвращается.
Embeddings памяти остаются отдельной моделью без изменений.

## Проверка результата

Один общий прогон штатных проверок после пакета изменений. Для нового поведения
нужны короткие содержательные проверки, а не тысячи дублирующих тестов:

- Bypass / явный локальный GPU не превращается в обязательный вопрос.
- Задача с файлом не уходит неявно в серверный голосовой STT.
- Отсутствующая возможность создаётся, применяется сейчас и повторно используется.
- Кандидат, не прошедший проверку, не заменяет рабочий релиз.
- После прерванной активации остаются история, Stop, Resume и восстановление.

Последние три пункта требуют реализации и живой проверки; одной правки prompt
для доказательства автономного саморазвития недостаточно.

## Согласованные решения

1. Prefill означает предварительную классификацию и маршрутизацию.
2. Laya испытана на CPU сервера и исключена по результатам; разбор делает Qwen.
3. Основа запуска и восстановления отделена от обновляемых частей приложения.
4. Приложение обновляется целым проверенным релизом с кратким перезапуском после
   завершения работы; горячая замена не требуется.
5. Саморазвитие выполняется в рамках задач пользователя. Постоянный фоновый
   цикл улучшений не создаётся.
