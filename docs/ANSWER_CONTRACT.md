## Черновик и принятие

`delta` показывает черновик; `step_started` начинает следующий шаг. Принятие
происходит через `final_response`, а `done` отдельно сообщает исход прогона.
Техническая ошибка и прерванный черновик не становятся успешным ответом в истории
и не должны озвучиваться как принятый результат. Потеря соединения после принятия
сама по себе не отзывает принятый текст. Продолжение delivery-сессии сохраняет
code-agent run ID.

Блок «Сделано / Проверено / Осталось» у края ответа `split_status_report` может
отделить в activity. Если другого содержательного текста нет, исходный ответ
сохраняется. Это форматирование отчёта, не отдельный вывод модели.

`done.ok`, `answer_status` и результат исходной задачи — разные факты. Критерии
пользователя и реальный артефакт проверяются отдельно от успешного завершения SSE.

## Приёмка

`AnswerAcceptance.evaluate` возвращает `retry` или `accept`, а координатор
применяет решение. Существуют отдельные флаги коррекции для источников, цитат,
доставки и других веток; новые неограниченные циклы проверки не добавляются.
Незавершённая перенесённая background job обрабатывается до финального ответа.

Модель не вызывает `task_decide` и `result_verify`: эти операции удалены.
`TaskOutcome` получает контракт пользователя и факты из результатов инструментов.
Его `verify_answer` сейчас возвращает пустой результат проверки. Наличие старых
полей или ветки проверки формата не означает действующую универсальную
аттестацию длины, смысла, полноты или правильности ответа.

Неподтверждённые требования, неудачная доставка, ошибки подтверждения цитат и
другие реализованные причины могут дать `answer_status=degraded`. Точный состав
веток и флагов находится в `answer_acceptance.py`; старый отчёт не расширяет его.

## Web и происхождение

`web_search`/`web_fetch` вызывают CLI установленного `web-research`. Native-адаптер
ведёт run-scoped `.web-research/<scope>/elira_pages.json`: адреса поиска,
ссылки со страниц, пользовательские URL, метки `S…`/`L…` и прочитанные страницы.
Неразрешённые адреса возвращают явную ошибку; придуманный URL не считается чтением.

Поиск, успешное извлечение текста и предъявление выдержки — разные состояния.
Совпадение адреса или хеша не подтверждает смысл вывода. Поля legacy-источников
и `[[source:id]]` сохраняют поддержку точной выдержки/цитаты; произвольная метка
из текста пользователя не создаёт runtime-квитанцию.

Текущий путь обычного ответа использует номера прочитанных страниц и Markdown
links. Приёмка раскрывает номера/метки, проверяет непрочитанные и индексные
страницы, сопоставляет пункты с текстом/датой и может перепривязать источник,
запросить допустимую коррекцию либо удалить неподтверждённый пункт/ссылку.
Различия quick/deep и явного Web-запроса реализованы в коде. Это проверка
происхождения с эвристиками, а не гарантия истинности всех утверждений.

Если Web явно запрошен, а подходящий локальный-only ответ не использовал Web,
существующая ветка добавляет указание, что ответ дан из памяти. Ошибки отдельных
операций и бюджетов видны в результатах и журнале. Старое обещание обязательного
финального блока диагностики SearXNG не является текущим контрактом.

Точные бюджеты quick/deep и повторное использование страниц принадлежат
[research.py](../skills/web-research/webskill/research.py). Native-вызов
останавливается по дедлайну навыка/транспорта или Stop; общая политика задачи
не делает Web бесконечным.

## Дословные цитаты

Общие числовые правила находятся в `shared/elira_common/quote_rules.py`;
`answer_contracts.py` — совместимый alias этого модуля. Названия в кавычках
не превращаются автоматически в запрос дословного цитирования.

Для цитат используется связь с конкретной показанной выдержкой. Неизвестный ID,
несовпадающий текст и неподтверждённый источник не становятся валидными из-за
наличия другого отрывка того же URL. Текущая приёмка имеет отдельную коррекцию
и обработку неподтверждённых цитат. Статус ссылки не оценивает весь пересказ.

## Выдача файла

1. Навык или обычный инструмент создаёт файл в рабочей папке.
2. `resource_publish` публикует текущие байты и возвращает канонический download
   URL, SHA-256 и сведения о ресурсе/локальном target, когда он известен.
3. `TaskOutcome` наблюдает фактическую попытку и receipt. Перед ответом и при
   продолжении проверяется актуальность; несовпавший receipt становится `stale`.
4. Неподтверждённая попытка либо download link получает существующую коррекцию.
   Если проблема сохраняется, ссылка становится обычным текстом и ответ — degraded.

Путь на диске, basename, stdout скрипта, preview и фраза модели не заменяют
публикацию. Внешняя ссылка на источник не требует локального артефакта. Кодовые
примеры URL не считаются обещанием выдачи. Каждая успешная публикация сохраняет
свой ресурс, даже если видимое имя совпадает с предыдущим.

`resource_materialize` работает по ResourceRef и точной связи ID/хеша; имя файла
само по себе не сопоставляет чужой ресурс. Внутренний storage path не становится
аргументом модели. Старые publication receipts остаются читаемыми для истории.

Публикация PDF/DOCX вызывает адаптер `skill_services/documents.py`, который
использует QA установленного `document-create`. Структура, рендер и проверяемые
квитанции относятся к конкретным байтам; утверждение модели не заменяет QA.
Неудачная QA не должна выдать успешный download artifact.

## Голос и диагностика

Автоозвучка использует принятый ответ; Markdown, кодовые блоки и служебные
указатели обрабатываются существующим speech owner. Stop/новая озвучка отменяет
очередь. Companion использует то же состояние ответа и речевые события.

Диагностику начинают с durable run ID и его журнала: запрос, tool arguments,
реальный результат, ограничения контекста, correction events, итоговый статус.
[AGENT_EVALS.md](AGENT_EVALS.md) описывает аудит уже завершённых запусков без нового
обращения к модели. Показанная ссылка, зелёный тест и смысловая приёмка задачи
фиксируются как отдельные доказательства.
