# Ответ, источники и диагностика

## Принятие ответа

`delta` — живой черновик (`answer_state=draft`). Новый `step_started` очищает
текст предыдущего шага. Единственное событие принятия — `final_response`:
его полный `text` заменяет черновик и становится версией для UI, истории и
автоматической памяти. `done` сообщает состояние прогона. Ошибка бюджета
передаётся через `done.error`, без принятия технической ошибки за ответ.
Автоматическое продолжение сохраняет тот же run ID.

До принятия Stop/ошибка оставляет видимый `interrupted`-черновик. Он не входит
в историю следующего запроса и не озвучивается. После принятия потеря соединения
не отзывает уже принятый ответ. Старые беседы без `answerState` читаются;
для истории/речи исключаются их ошибки и отменённые ходы.

TTS получает принятый текст без оформления Markdown и указателей источников.
Кодовые блоки не читаются. Длинная речь передаётся последовательно частями до
2000 символов без прежнего отбрасывания конца. Stop или новая озвучка отменяет
очередь, включая ещё не полученный результат синтеза.

## Происхождение веб-данных

Путь остаётся существующим: web tools → ToolExecutor → RunEvidence → RunJournal
→ SSE → сохранённый AgentTurn. Нового реестра, базы или исполнителя нет.

| Статус | Значение |
|---|---|
| `discovered` | Поиск вернул URL; страница ещё не прочитана |
| `fetched` | Corpus сохранил страницу; паспорт не равен предъявлению текста |
| `excerpt` | Получен конкретный текстовый фрагмент |
| `failed` | Ошибка конкретной страницы, без выдержки |

Смешанный batch `web_fetch` сохраняет `ok=true`, если хотя бы одна страница
прочитана. Ошибочные страницы сохраняют индивидуальный `failed`. Пустой
`web_query` возвращает `ok=false/no_results`. Результаты, не прошедшие существующий
`verify_quote`, не попадают ни в текст, ни в структурированный список.

Запись содержит runtime ID, исходный run ID, URL, время, хеш полученного текста,
хеш выдержки, выдержку и, для Corpus, `doc_id/chunk_id/offset`. В обычном fetch
хеш относится к извлечённому тексту; в Corpus — к каноническому документу.
Это не хеш исходного HTTP-ответа. Изменение текста создаёт другой ID.

`presented` означает, что точный фрагмент с ID сохранился в упакованных сообщениях
перед вызовом модели. Одного URL, паспорта, summary или скопированного
пользователем маркера недостаточно. Web-данные остаются недоверенными и не
переносятся в блок проверенных локальных фактов.

## Ссылки и продолжение

Модель ставит `[[source:id]]` рядом с выводом по выдержке. `final_response`
передаёт `sources`, `citations`, `source_status`. Сопоставленная ссылка получает
`status=matched` и исходный фрагмент; неизвестный или не предъявленный ID —
`unresolved`, без кликабельной ссылки. До принятия UI показывает ожидающий маркер.
Обычные URL, Markdown-ссылки и примеры в коде продолжают работать.

**`matched` проверяет происхождение, а не смысл вывода.** Поле
`claim_support=not_assessed` сохраняется независимо от корректности ссылки.
Универсального переписывания ответа и обязательного LLM-судьи нет.

RunJournal хранит снимки в существующем `web_sources`. Compaction закрепляет
точные выдержки отдельно от summary; приоритет упомянутых ID сохраняется при
пересборке и Resume. Набор ограничен 128 записями, выдержка — 1500 символами,
блок контекста — 7000 символами, включая заголовок. Это ограниченная рабочая
память, не обещание бессрочного удержания всех прочитанных страниц.

Следующий ход передаёт до 8 `source_run_ids`. Сервер читает собственные журналы,
проверяет принадлежность чату и принятие ответа, затем восстанавливает только
сопоставленные ID из истории. Клиентские выдержки не принимаются. Снимок
сохраняет исходную версию после истечения TTL временного Corpus; свежесть
страницы при этом не утверждается. Для новых данных нужен новый fetch.

Структурированные источники реализованы для встроенных
`web_search/web_fetch/web_query`. Остальные источники наблюдений, включая MCP,
сохраняют прежние контракты и не получают фиктивных web receipts.

## Повторяемая диагностика

```powershell
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --output .agent/evals/answer-contract/capture
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --live --compare-dry --seeds 41,42,43 --output .agent/evals/answer-contract/live
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --live --replay .agent/evals/answer-contract/live/cases.json --output .agent/evals/answer-contract/replay
```

Без `--live` — только захват первого запроса публичного `stream_code_agent`.
С `--live` — повтор через существующий provider, без исполнения предложенных
моделью tools. Изолированное состояние создаётся внутри каталога отчёта;
личная память не меняется. Сохраняются точный payload без заголовков авторизации,
seed, размеры prompt/schema, хеш префикса, настройки сервера, сырой ответ,
reasoning и метрики. Диагностический лимит вывода — 1024 токена;
production sampling не меняется.

Сравниваются минимальная личность, полный рабочий контекст, мужской род
в истории, compaction, настроение, thinking и опциональная абляция DRY.
Смысловые фикстуры отдельно проверяют границы обобщения, отрицание, единицы и
несопоставимые результаты. Их рубрика сохраняется в `expected`; оценку смысла
делает ревьюер. Сопоставление ID не заменяет эту оценку.

`ttft_ms` модели может относиться к reasoning; `first_answer_ms` измеряет первое
событие текста ответа. Новые префиксы, тёплые повторы и смена thinking анализируются
раздельно по фактическим cache-метрикам. Этот replay не измеряет UI и не заменяет
smoke через `/api/code-agent/stream` и браузер.
