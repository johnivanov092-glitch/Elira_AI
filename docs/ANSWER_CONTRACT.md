# Ответ, источники и диагностика

## Принятие ответа

`delta` — живой черновик (`answer_state=draft`). Новый `step_started` очищает
текст предыдущего шага. Единственное событие принятия — `final_response`:
его полный `text` заменяет черновик и становится версией для UI, истории и
автоматической памяти. `done` сообщает состояние прогона. Ошибка бюджета
передаётся через `done.error`, без принятия технической ошибки за ответ.
Автоматическое продолжение сохраняет тот же run ID.

До принятия Stop/ошибка оставляет видимый `interrupted`-черновик. Он не входит
в историю следующего запроса и не озвучивается. После принятия потеря соединения
не отзывает уже принятый ответ. Старые беседы без `answerState` читаются;
для истории/речи исключаются их ошибки и отменённые ходы.

TTS получает принятый текст без оформления Markdown и указателей источников.
Кодовые блоки не читаются. Длинная речь передаётся последовательно частями до
2000 символов без прежнего отбрасывания конца. Stop или новая озвучка отменяет
очередь, включая ещё не полученный результат синтеза.

## Выдача файлов в чат

Qwen объявляет намерение через `runtime_control(task_decide)`:
`config.delivery={mode:"chat_download",targets:[локальные пути]}`. Для задачи
без выдачи файла — `mode:"none", targets:[]`. Слова «скачать» в цели дают только
подсказку; реализация кнопки скачивания не требует артефакта в текущем чате.
Это отдельный список от `task_decide.targets` и `result_verify.targets`.
Повторный `task_decide` без `delivery` сохраняет прежнее решение; явная замена
с `reason` позволяет исправить ошибочный путь или снять неверное обязательство.

В отсутствие декларации реальные попытки `resource_publish` задают проверяемые
пути, включая неудачные попытки. Явный новый контракт заменяет этот список;
история неудач сохраняется, но не заставляет публиковать файл с прежней опечаткой.
Успешная прямая публикация допустима и без предварительной декларации.

Один владелец `TaskOutcome` хранит receipts `resource_publish`, `file_gen` и
опубликованной локальной GPU-транскрипции. Receipt связывает канонический download
URL и SHA-256 сохранённой копии с реальным локальным target, когда он известен.
Для `ResourceRef` materialize может добавить точный путь по ID и хешу ресурса;
путь не угадывается из basename. Несопоставленный артефакт не закрывает local target.
Перед принятием и после Resume сверяются фактические байты; изменённая публикация
становится `stale` и не оживает только от возврата старых байтов. Download URLs
и статусы сохраняются в журнале и закреплённом контексте; внутренний storage path
ресурса не передаётся модели.

Неподтверждённые targets и канонические Markdown/autolink-ссылки вида
`/api/skills/download/...` получают одну корректировку. Затем ответ становится
`degraded`: сохраняется полезная проза, добавляется точная диагностика, ошибочная
ссылка перестаёт быть кликабельной. Примеры внутри inline/fenced code не считаются
выдачей файла. Это узкая проверка публикаций, не универсальная оценка смысла ответа;
внешние ссылки на источники не требуют локального артефакта. Typed BOM/document QA
сохраняют свои отдельные проверки и канонические ответы.

## Происхождение веб-данных

Путь остаётся существующим: web tools → ToolExecutor → RunEvidence → RunJournal
→ SSE → сохранённый AgentTurn. Нового реестра, базы или исполнителя нет.

| Статус | Значение |
|---|---|
| `discovered` | Поиск вернул URL; страница ещё не прочитана |
| `fetched` | Corpus сохранил страницу; паспорт не равен предъявлению текста |
| `excerpt` | Получен конкретный текстовый фрагмент |
| `failed` | Ошибка конкретной страницы, без выдержки |

Смешанный batch `web_fetch` сохраняет `ok=true`, если хотя бы одна страница
прочитана. Ошибочные страницы сохраняют индивидуальный `failed`. Пустой
`web_query` возвращает `ok=false/no_results`. Результаты, не прошедшие существующий
`verify_quote`, не попадают ни в текст, ни в структурированный список.

Запись содержит runtime ID, исходный run ID, URL, время, хеш полученного текста,
хеш выдержки, выдержку и, для Corpus, `doc_id/chunk_id/offset`. В обычном fetch
хеш относится к извлечённому тексту; в Corpus — к каноническому документу.
Это не хеш исходного HTTP-ответа. Изменение текста создаёт другой ID.

`presented` означает, что точный фрагмент с ID сохранился в упакованных сообщениях
перед вызовом модели. Одного URL, паспорта, summary или скопированного
пользователем маркера недостаточно. Web-данные остаются недоверенными и не
переносятся в блок проверенных локальных фактов.

## Ссылки и продолжение

Модель ставит `[[source:id]]` рядом с выводом по выдержке. `final_response`
передаёт `sources`, `citations`, `source_status`. Сопоставленная ссылка получает
`status=matched` и исходный фрагмент; неизвестный или не предъявленный ID —
`unresolved`, без кликабельной ссылки. До принятия UI показывает ожидающий маркер.
Обычные URL, Markdown-ссылки и примеры в коде продолжают работать.

**`matched` проверяет происхождение, а не смысл вывода.** Поле
`claim_support=not_assessed` сохраняется независимо от корректности ссылки.
Универсального переписывания ответа и обязательного LLM-судьи нет.

Для явной дословной цитаты рядом с source-меткой дополнительно проверяется
непрерывное совпадение её текста именно в указанном `excerpt`, с валидным хешем,
`quote_verified=true` и предъявлением в текущем контексте. Совпадение URL с другим
отрывком не подходит. Неверная метка остаётся `unresolved`; одна корректировка
ответа сохраняется после Resume, повторное нарушение даёт `degraded`.
Обычный пересказ сохраняет проверку происхождения без оценки смысла.

Обычный веб-ответ не требует `task_decide`: поиск и чтение завершаются содержательным
ответом либо используются в следующих этапах исходной задачи. Прямые пользовательские
ограничения проверяются и без модельной декларации. При наличии явно объявленного
контракта `task_decide.config.requirements[].verification={checks:[...]}`
может явно объявить механические проверки: `web_search(query,url)`,
`source_read(url,contains?)`, `answer_format(contains?,max_chars?,language?,markdown_url?)`,
`cited_quote(url,count,max_words)`, `tool_policy(allowed,max_search_queries?,max_read_urls?)`,
`no_persistence` (проверка запрещённых пользователем каналов rag/direct_memory/learning).
Поля `answer_format` необязательны, но требуется хотя бы одно. Лимиты поиска,
чтения, длины и обязательные слова проверяются только по распознанным прямым
условиям пользователя, независимо от наличия модельного predicate. `user_quote`
сохраняет происхождение условия, но сам по себе не разрешает придуманный лимит.
Без прямого запрета памяти модельный `no_persistence` не создаёт новый запрет;
явная runtime policy с отключёнными каналами остаётся обязательной.
`web_search(query,url)` связывает URL с конкретным запросом, в том числе внутри
пакета: native tool передаёт `query_sources` с canonical source IDs для каждого
запроса. Старый пакет без такой привязки не подтверждает происхождение URL от
отдельного запроса; одиночные исторические вызовы остаются совместимыми.
`language` проверяет преобладание соответствующего алфавита в прозе вне цитат,
кода и подписей ссылок. Подтверждённые прочитанным отрывком английские названия
в полях списков и таблиц не определяют язык русских пояснений. Текст ответа и
сами названия не переписываются;
это проверка формы, не понимания текста. Runtime связывает verdict каждого ID с
revision, input version и SHA-256 фактического кандидата ответа. Один успешный
инструмент не подтверждает остальные требования; непроверяемые условия остаются
`unconfirmed`. Такие receipts не используются для обучения или проверки файлов.
Коррекция перечисляет проваленные виды checks, сохраняя прежний предел повторов.
При исчерпании коррекции полезный ответ с внешними источниками сохраняется вместе
с перечнем неподтверждённых условий. Это не подтверждает смысловую правильность.
Структурированные ошибки SearXNG доходят до ответа отдельным текстовым блоком;
произвольный текст страниц не становится таким предупреждением.

Эта ветка допускает отсутствие декларации либо `one_off`, пустые inputs/targets, delivery none и полную историю
допустимых вызовов текущего запуска. Команды, изменения, прежние
файловые контракты и импортированная неполная история исключают её. Лимиты поиска
учитывают неудачные попытки; чтение учитывает все запрошенные URLs, включая повторы.
`web_fetch(store=true)` допускается только при разрешённом сохранении по политике
задачи: RAG разрешён либо direct memory разрешена для всей задачи. При неизвестной
политике, отключённой памяти или разрешении только отдельных фактов запись в
семидневный кеш блокируется до ingest. `fetched` паспорт не подтверждает чтение;
проверка требует предъявленного verified excerpt из последующего `web_query`.
Другие `store=true` операции этой веткой не подтверждаются.

Поиск и чтение используют согласованный потолок представления 120000 символов
в native tool, реестре executor и передаче в модель. Меньшее окно контекста может
уменьшить объём с явной пометкой; обрезанные фрагменты не считаются предъявленными.
Полный текущий префикс Elira не помещается в 8K: такой профиль останавливается
до первого вызова модели с `context_budget_exceeded`. Упаковка веб-выдержек
проверена в основном контуре 32K и 128K; она не сокращает обязательные инструкции.
Реестр происхождения хранит до 1024 source records: пакет 30×30 поисковых ссылок
не теряет первые результаты из-за прежнего ограничения 128. Эти лимиты не обещают
поместить одновременно полный текст 30 страниц по 80000 символов.
Предупреждения движков SearXNG сохраняются также при пустом или неуспешном поиске.
Итоговый технический notice формируется из фактических ошибок инструментов до
проверки ответа: отсутствие предупреждения в черновике модели его не скрывает.
Он входит в предъявленный текст, ограничения длины и SHA проверенного ответа;
языковая проверка применяет существующее правило для блоков кода. Notice не
создаёт источник и не превращает неуспешный поиск в выполненное требование.

Совпадение цитаты и SHA доказывает предъявление данных, а не правильность всех
выводов модели. Веб-вывод должен сохранять ограничения источника: компонент,
ветку версии, платформу, магазин, регион и дату. В анализе безопасности нельзя
сравнивать исправленные версии разных веток одним общим >=, объявлять весь сервис
безопасным по версии отдельного компонента или называть найденную ссылку прочитанной.
Файлы по-прежнему проверяются `result_verify` с текущими хешами и отдельным отчётом.

Если пользователь явно ограничил число слов в цитате, перед принятием ответа
детерминированно проверяются выделенные цитаты; явная подпись количества слов
пересчитывается без изменения текста цитаты.
Нарушение допускает одну корректировку по уже прочитанным источникам. Повторное
нарушение возвращает `answer_status=degraded`, без выдачи ошибочной цитаты как
готового ответа. Лимит и факт корректировки сохраняются в RunJournal и действуют
после Resume. Это проверка формата, а не дословности или смысла цитаты.
Журнал сохраняет `answer_status`; ответ с `degraded` не получает статус
завершённой задачи `completed`.

Ссылка ответа на страницу, текст которой не прочитан (решение 2026-10-06, как с
неподтверждёнными цитатами 2026-10-03): одна корректировка; если она не помогла,
ответ модели сохраняется, а у каждой такой ссылки убирается адрес — остаётся текст
с пометкой о ЭТОЙ странице (не о сайте): «(ссылка убрана: страница не прочитана)» или
«(ссылка убрана: не открылась — причина)» из журнала прогона
(`answer_contracts.mark_unread_web_links`), `answer_status=degraded`. Раньше весь
ответ заменялся на «Подтвердить исходный ответ … не удалось» (выбрасывал, например,
верную таблицу CVE с прочитанной nginx.org из-за ссылок на неоткрытые бюллетени F5).

В веб-ответе числовая периодичность обновлений должна иметь ссылку на реально
предъявленный источник в том же абзаце, пункте или строке таблицы. Для распознанных
чисел, включая простые числительные словами, в процитированном фрагменте должны
присутствовать совпадающие число и единица времени. Ссылка на список версий без
периода, ссылка соседнего пункта или общий список источников не подходят.
При пропуске разрешена одна корректировка: модель проверяет число, единицу
и тот же объект/канал либо убирает неподтверждённую деталь. Повторный пропуск
даёт `degraded`; попытка сохраняется после Resume. Проверка узкая: это покрытие
ссылками, не доказательство смысла; `claim_support=not_assessed` не меняется.

`web_fetch` отдельно показывает фактические подписи и адреса ссылок из основного
текста страницы: до 20 ссылок и 3200 символов. Этот недоверенный список помогает
выбрать следующую страницу; содержимое адресата считается прочитанным только
после отдельного fetch. Текстовые выдержки и их смещения от списка не меняются.
При пакетном чтении общий бюджет инструментального сообщения распределяется
между страницами до упаковки, чтобы общее усечение не удаляло средние страницы.
Receipts формируются из точного сохранённого текста, сокращения отмечаются.

RunJournal хранит снимки в существующем `web_sources`. Compaction закрепляет
точные выдержки отдельно от summary; приоритет упомянутых ID сохраняется при
пересборке и Resume. Набор ограничен 128 записями, выдержка — 1500 символами,
блок контекста — 7000 символами, включая заголовок. Это ограниченная рабочая
память, не обещание бессрочного удержания всех прочитанных страниц.
Восстановленный блок передаётся как недоверенные входные данные с серверным
идентификатором, а не как начало ответа ассистента: chat template не должен
продолжать служебные выдержки вместо ответа на исходный запрос.

Следующий ход передаёт до 8 `source_run_ids`. Сервер читает собственные журналы,
проверяет принадлежность чату и принятие ответа, затем восстанавливает только
сопоставленные ID из истории. Клиентские выдержки не принимаются. Снимок
сохраняет исходную версию после истечения TTL временного Corpus; свежесть
страницы при этом не утверждается. Для новых данных нужен новый fetch.
Resume обычного запроса продолжает его по сохранённым данным и источникам.
Требования проверять файлы и обновлять чеклист относятся только к структурным
задачам с delivery-контрактом.

Структурированные источники реализованы для встроенных
`web_search/web_fetch/web_query/browser`. У браузера receipt создаётся только после
успешного чтения непустого DOM и завершения запрошенных действий, по фактическому
конечному URL; текст команд click/fill не включается в цитируемые выдержки.
Остальные источники наблюдений, включая MCP,
сохраняют прежние контракты и не получают фиктивных web receipts.

Ответ по прочитанным веб-источникам пишет сама модель своими словами (суть,
вывод, структура) со ссылками на прочитанные источники — решение Джона
2026-10-05; режим source-first (ответ = набор дословных цитат) удалён.
Проверки происхождения остаются: ссылка рядом с утверждением должна вести на
прочитанную страницу, ID источника обязан существовать, дословные цитаты
сверяются с выдержками (названия в «ёлочках» цитатами не считаются).

Путь веб-вопроса (прогон без правок, выдачи файлов и фоновых задач):

1. Прочитать сайт 1, сайт 2. После 2-го прочитанного сайта результат чтения
   получает пометку «прочитано N из L»: хватает — модель отвечает, не хватает —
   читает следующий сайт.
2. Лимит L = 10 сайтов на вопрос; 20 — только если пользователь прямо просит
   глубокий/подробный анализ, обзор, исследование или называет число сайтов
   больше 10 (`answer_contracts.explicit_web_site_limit`; решение 2026-10-06,
   было 5/10). Считаются страницы, чей текст прочитан
   (`RunEvidence.read_site_urls`), а не сниппеты поиска. Страница со стеной
   входа или проверкой от ботов (Reddit и т. п.) — неудачное чтение, в лимит не
   идёт: модель берёт следующий результат выдачи.
3. На лимите новые сайты не читаются (лишние адреса пакета `web_fetch`
   отбрасываются с пометкой), следующий ход модели идёт без инструментов:
   ответ по прочитанному, чего нет — сказать прямо.
4. Повтор веб-операции без новых данных в таком прогоне ведёт к тому же ходу
   «ответ по прочитанному», а не к «Задача не завершена».

За один вызов `web_search`/`web_fetch` — до 5 запросов/адресов.

Путь модели (подсказка в веб-инструкции, кодом полнота не проверяется): разбить вопрос
на 3–5 частей и искать по всем одним пакетом; хватает по каждой части → ответ, нет →
дочитать по ней; не открылась страница → следующая из выдачи; ответ по частям со
ссылками на прочитанное, в конце «Не нашла: …».

Неоткрывшиеся страницы (решение 2026-10-06) модель больше не перечисляет: интерфейс
сам показывает под принятым ответом строку «Не открылись: сайт — причина» из
`final_response.sources` (status `failed`). Страница, которая в том же прогоне всё же
прочиталась, и неудачный `find` по открытой странице туда не попадают. В текст ответа
код ничего не дописывает.

Среда поиска (решение 2026-10-06, вариант «в»): модель сама указывает в
`web_search(audience)` `global` (общая тема — техника, игры, наука, софт, мировые
события) или `regional:<страна>` (вопрос о стране/регионе — язык её аудитории, её СМИ).
Код следит только за последствием: при `global` среди запросов прогона должны быть и
русские, и английские; иначе поиск не выполняется и модель получает просьбу добавить
второй язык (не больше двух отказов за прогон — без зацикливания). `regional` не
ограничивается. Без объявленной среды — одно напоминание в результате первого поиска.
Новости и факты о событиях: у каждого — номер прочитанного источника (пишут несколько —
все номера) и дата события из самого материала; старое как новое не подаётся. Правило
«два источника, иначе пометка» снято 2026-10-06 (вариант «Б»): сколько источников у
факта, видно по числу ссылок.

Ссылки по номерам (решение 2026-10-06, практика индустрии): каждая прочитанная страница
получает номер в результате инструмента («[Номер для ссылок в ответе: [3] url …]», тот же
номер в сохранённых выдержках). Модель пишет `[Название][n]` или `[n]`; перед выдачей
`answer_contracts.render_numbered_citations` превращает их в `[Название](url)` и
`[сайт](url)` — вид ответа как в прогоне 479bec3d, но адрес берётся только из списка
прочитанного. Неизвестный номер убирается (подпись остаётся текстом), код в ответе не
трогается, к ответу ничего не дописывается. Проверка Markdown-ссылок на непрочитанные
страницы остаётся подстраховкой, если модель всё же напишет адрес сама.

## Повторяемая диагностика

```powershell
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --output .agent/evals/answer-contract/capture
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --live --compare-dry --seeds 41,42,43 --output .agent/evals/answer-contract/live
backend\.venv\Scripts\python.exe -X utf8 backend\tests\smokes\answer_contract_eval.py --live --replay .agent/evals/answer-contract/live/cases.json --output .agent/evals/answer-contract/replay
```

Без `--live` — только захват первого запроса публичного `stream_code_agent`.
С `--live` — повтор через существующий provider, без исполнения предложенных
моделью tools. Изолированное состояние создаётся внутри каталога отчёта;
личная память не меняется. Сохраняются точный payload без заголовков авторизации,
seed, размеры prompt/schema, хеш префикса, настройки сервера, сырой ответ,
reasoning и метрики. Диагностический лимит вывода — 1024 токена;
production sampling не меняется.

Сравниваются минимальная личность, полный рабочий контекст, мужской род
в истории, compaction, настроение, thinking и опциональная абляция DRY.
Смысловые фикстуры отдельно проверяют границы обобщения, отрицание, единицы и
несопоставимые результаты. Их рубрика сохраняется в `expected`; оценку смысла
делает ревьюер. Сопоставление ID не заменяет эту оценку.

`ttft_ms` модели может относиться к reasoning; `first_answer_ms` измеряет первое
событие текста ответа. Новые префиксы, тёплые повторы и смена thinking анализируются
раздельно по фактическим cache-метрикам. Этот replay не измеряет UI и не заменяет
smoke через `/api/code-agent/stream` и браузер.
